# uemulator

Minimal embeddable x86_64 system emulator in Rust. Boots an unmodified Linux bzImage with a virtio console (`hvc0`; the 16550 serial port is always present and carries early boot text), through the built-in UEFI firmware by default (or directly, with no firmware). Design is modeled on QEMU TCG: decode to micro-ops, TB cache, interpreter plus aarch64, x86_64 and WebAssembly host JITs with runtime fallback.

Read `plans/README.md` first; the plans are the source of truth for design and milestones (`plans/10-milestones.md` for current status).

## Commands

- Run: `cargo run --release -- quick create test --install debian` then `-- quick boot test` (a named machine in `~/.uemulator/machines/test/`: `machine.toml`, the netboot kernel and initramfs in `artifacts/`, sparse disks; `UEMULATOR_HOME` moves `~/.uemulator`; `quick update-artifacts test` refetches and `quick reinstall test --install alpine` swaps the distro and keeps the disk; `quick create` gives a machine a NAT NIC by default so the installers can reach their mirrors) or `-- advanced boot --kernel K --initramfs I`
- Web: `./hack/web.sh serve` builds `crates/uemulator-web` for `wasm32-unknown-unknown` and the UEFI firmware the page boots through for `x86_64-unknown-none` (`rustup target add` both first) into `target/web` and serves it on :8080 (needs the COOP/COEP headers `hack/web/serve.py` sends; where a server cannot, `www/isolation_worker.js` adds them, which is how `.github/workflows/pages.yml` publishes it to GitHub Pages under `/web/` on every push to main; `WEB_DEMO=1` adds the one-button Alpine demo, `hack/web/demo.py`); `cargo clippy --release --target wasm32-unknown-unknown -p uemulator-web` must print zero warnings too
- WebAssembly JIT: `cargo test --release --target wasm32-wasip1 -p uemulator --lib -- --test-threads=1 jit::` runs the differential corpus on the wasm backend under Node (`rustup target add wasm32-wasip1`; the runner is `hack/wasm/test-runner.sh`); run it after touching `jit/wasm*.rs`, `jit/emit_wasm.rs` or `www/jit_host.js`, and `cargo clippy --release --target wasm32-wasip1 -p uemulator --all-targets` must print zero warnings. A panic aborts the whole run (wasm cannot unwind): filter to one module to find the test. `node hack/wasm/boot.mjs --kernel K --initrd I [--disk IMAGE] [--firmware none|uefi|bios] [--iommu] [--no-jit] [--until TEXT]` boots a real kernel on the built `target/web/uemulator_web.wasm` (`hack/web.sh` first) and times it (`plans/13-web.md`)
- UEFI: `./hack/uefi/boot.sh [x86_64|aarch64]` builds `crates/uemulator-uefi` and boots it in QEMU (accelerated when the host matches; `UEFI_ACCEL=hv|emu` picks hardware virtualization or the emulator, and `-cpu max,svm=on` under TCG exercises the SVM path); `cargo clippy --release --target x86_64-unknown-uefi -p uemulator-uefi` (and `aarch64-unknown-uefi`) must print zero warnings too
- Firmware: `--firmware uefi|bios|none` (on `quick create`/`edit` and `advanced boot`), `uefi` by default: the built-in UEFI firmware boots the disk, or the `--kernel`/`--initramfs` it is given (QEMU `-kernel` under OVMF style: the kernel needs an EFI stub, else the boot fails and says to use `--firmware none`; `plans/19-uefi-firmware.md`). `none` enters any bzImage directly in 64-bit mode (what `--verify` and the library's fake-kernel tests use); `bios` boots a disk through the library's BIOS (`MachineConfig::boot_disk`, `plans/17-bios.md`). A `machine.toml` without a `firmware` key is `uefi`
- Disk images: `-- disk create F.udisk --size MIB` (or `--backing BASE`, a path relative to F or an http(s) URL: a copy-on-write overlay), `-- disk convert SRC DST` (raw <-> udisk by DST's extension, flattens overlays), `-- disk info IMAGE`. `--disk` takes raw or udisk and finds an overlay's base itself; new machines get `disk-<n>.udisk`. The format is `docs/spec/uemulator-disk-format.md`; change the spec with the code (`disk/udisk.rs`)
- Disk boot: `quick boot NAME` boots a machine whose disk has an install on it through the machine's firmware; `--boot-from installer` runs the installer instead (through UEFI for `uefi` machines, with the machine's `nvram.kv`)
- Firmware / real mode: `uemulator advanced boot-firmware --firmware IMAGE` (image ends at 1 MiB, CPU starts in real mode at F000:FFF0); a bzImage without a 64-bit entry boots in 32-bit protected mode (`plans/15-legacy-modes.md`)
- Linux KVM check: `hack/kvm/run.sh` loads `kvm_amd` in the emulated guest and runs vCPUs in every CPU mode on the emulator's SVM (needs `unsquashfs`, a musl cross gcc, the Alpine artifacts and network for the modloop); run it after touching `cpu/svm.rs`, paging or the 16/32-bit modes
- Test: `cargo test --release --workspace` (also `-p uemulator --no-default-features`)
- SMP: `--cpus N` gives the guest N vCPUs, each on its own host thread when the host has threads and a clock (`--smp auto`, the default); `--smp timeshare` takes turns on one thread, deterministic on the virtual clock (`plans/22-smp-threads.md`). A freestanding embedder gets threads only through `MachineConfig::thread_spawner` and a `host_clock`
- Before EVERY commit: run `./hack/autofix.sh` (clippy --fix + fmt), then fix by hand every warning it leaves; `cargo clippy --release --all-targets` must print zero warnings. Never commit with warnings.

## Rules

- Cargo workspace: `crates/uemulator-uefi` (`no_std` UEFI app; on hosted targets only its hardware-independent modules build, which is what `cargo test -p uemulator-uefi` runs), `crates/uemulator` (library; `no_std` + `alloc` when `freestanding`; the default `jit` feature pulls in `libc` on unix and `windows-sys` on Windows (and enables the WebAssembly backend on wasm32), `--no-default-features` has zero dependencies and is interpreter-only), `crates/uemulator-cli` (clap, ureq; may use crates freely) and `crates/uemulator-web` (wasm32 only, empty elsewhere; C ABI plus `www/`). `cfg(freestanding)` (from `crates/uemulator/build.rs`: UEFI and wasm32 except WASI, which is the hosted test target) replaces `target_os = "uefi"` in the library. Tests live next to the code in each crate; the library's shared helpers are in `crates/uemulator/src/testkit.rs`.
- `lib.rs` is the entire public API: `EmulatedMachine::new(cfg)` then `start()`. Everything else is `pub(crate)`.
- The library never touches stdio, never calls `process::exit`, holds no global mutable state, never panics on guest behavior. Guest faults are guest exceptions.
- Comment what is surprising, looks obscure, or is named something non-obvious: hardware quirks, ordering constraints, invariants the JIT relies on, why a value is what it is. Cite the SDM section or the QEMU behavior when that is the real source. Don't restate what the code says.
- Write comments for the next Claude who has to change this without having seen the history. Say what breaks if the code is changed carelessly. Plain, terse prose like a human maintainer would write: no "This function...", no filler, no banner or section-divider comments.
- Prefer descriptive names. Don't shorten to 3-5 letters when a real word reads better; rename when you touch something badly named. Architectural names from the Intel/AMD manuals (`cr0`, `efer`, `rip`, `gdtr`, `cpl`, `mxcsr`) stay as-is.
- No magic constants. Name register bits, MSR numbers, descriptor flags, vector numbers, sizes and timeouts as `const`s at the narrowest scope that makes sense, and let comments refer to the name.
- `../ext/qemu-uplink` is read-only reference (see `plans/09-qemu-map.md`). Study behavior; write Rust from scratch, don't transliterate.
- The interpreter is the oracle for the JIT. Any new uop gets an interpreter implementation and a test first.
- Advertise a CPUID bit only together with the tests for the instructions behind it.
- JIT blocks are position independent: keyed by physical address, and every guest `rip` a block uses is the page base (`PAGE_BASE`) plus a translation-time offset (`Gen::rip_to`); never embed a guest virtual address in generated code (`plans/06-jit.md`). The code cache is shared by all vCPUs: add or patch code only under its lock, and patch links with `ExecMem::write_word`.
- With threads (`plans/22-smp-threads.md`) RAM and the devices are shared. Take the device lock through `cpu.dev.lock()` for every device access and never hold it into `Cpu::with_exclusive` (the others may be waiting for it). Guest memory goes through `mem_read`/`mem_write` (acquire/release, atomics), not through slices, whenever another vCPU could be writing it. Anything machine-wide you add to `Cpu` needs a decision twice: `swap_shared` for time-sharing, and shared handle or private copy for threads.
- Debug-profile is optimized (`opt-level = 3`) because the kernel decompressor is ~1e9 guest instructions.

## Tests

- Unit tests only: no network, no cached kernels or initrds, nothing under `~/.uemulator`. A test that needs a guest builds a tiny one: `testkit::FakeKernel` makes a valid bzImage whose 64-bit entry point is hand-assembled code (`echo 'mov rax, 5; hlt' | hack/asm.sh` prints the bytes; `BITS=16` or `BITS=32` assembles for real mode or 32-bit protected mode).
- `testkit::Harness` runs a snippet on one CPU, interpreter or JIT, with undelivered faults reported as `Stop::Fault`; `testkit::run_machine` boots a fake kernel on a full `EmulatedMachine`.
- Anything the JIT compiles gets a case that runs `testkit::assert_jit_matches_interpreter`. The interpreter is the oracle. The same corpus runs on the WebAssembly backend (above), so a form the wasm generator lowers needs no case of its own beyond a differential run there.
- Fixing a bug: write the failing test first.
- Threaded tests (`testkit::run_threads`, `machine/tests.rs` with `SmpMode::Threads`) are the ones that catch memory-ordering and atomicity bugs, and only on a native aarch64 host (Rosetta runs x86 with hardware TSO). When you change the atomics or the ordering, remove the thing under test and watch the test fail before trusting it.
- Under Rosetta (`--target x86_64-apple-darwin`) tests that run generated code take turns through `jit::serialize_jit_tests`; Rosetta's translation cache goes stale when one thread frees a code buffer and another maps one at the same address. `testkit::Harness::enable_jit` holds it for you; take it yourself when you use `Jit::new` directly.
- Real-kernel lockstep check (not a test, needs a kernel you supply): `--verify` on the CLI.
- Real boot loader check (not a test, needs a disk an installer wrote): `quick boot NAME --realtime` on an installed Alpine machine with `--firmware bios` (new machines are `uefi`); run it after touching `cpu/bios.rs`.

## Debugging

- `--debug` on the CLI dumps CPU state and scans guest RAM for the kernel log ring buffer on exit.
- `--verify` runs the JIT in lockstep with the interpreter and stops at the first diverging block; use it after any change under `crates/uemulator/src/jit/`. Do not type into it: host input reaches only the JIT side's console, so the first keystroke shows up as a bogus divergence at an interrupt entry (boot to the shell prompt and stop instead).
- `--time <unix>` fixes the RTC; guest behavior must not depend on it, so a time-dependent failure is an emulator bug.
- On an Apple Silicon Mac the x86_64 JIT runs under Rosetta: `cargo test --release -p uemulator --target x86_64-apple-darwin` (`rustup target add x86_64-apple-darwin`).
