# uemulator

Minimal embeddable x86_64 system emulator in Rust. Boots an unmodified Linux bzImage with a virtio console (`hvc0`; the 16550 serial port is always present and carries early boot text), through the built-in UEFI firmware by default (or directly, with no firmware). Design is modeled on QEMU TCG: decode to micro-ops, TB cache, interpreter plus aarch64, x86_64 and WebAssembly host JITs with runtime fallback.

Read `docs/plans/README.md` first (`docs/README.md` indexes all the docs by topic); the plans are the source of truth for design and milestones (`docs/plans/10-milestones.md` for current status).

## Commands

- Run: `cargo run --release -p uemulator-cli -- quick create test --install debian` then `-- quick boot test` (a named machine in `~/.uemulator/machines/test/`: `machine.toml`, the netboot kernel and initramfs in `artifacts/`, sparse disks; `UEMULATOR_HOME` moves `~/.uemulator`; `quick update-artifacts test` refetches and `quick reinstall test --install alpine` swaps the distro and keeps the disk; `quick create` gives a machine a NAT NIC by default so the installers can reach their mirrors) or `-- advanced boot --kernel K --initramfs I`
- Web: `./hack/web.sh serve` builds `crates/uemulator-web` for `wasm32-unknown-unknown` and the UEFI firmware the page boots through for `x86_64-unknown-none` (`rustup target add` both first) into `target/web` and serves it on :8080 (needs the COOP/COEP headers `hack/web/serve.py` sends; where a server cannot, `www/isolation_worker.js` adds them, which is how `.github/workflows/pages.yml` publishes it to GitHub Pages under `/web/` on every push to main; `WEB_DEMO=1` adds the Alpine Linux and Edera Xen demo buttons, `hack/web/demo.py`, with Xen's image pinned by digest in `hack/web/demo-xen.ref`); machines in tabs of the same page share one Ethernet segment with DHCP (the Network switch, `?network=0` off; `SegmentAgent` in the library, `www/segment.js`), and `node hack/wasm/segment.mjs` (after `WEB_DEMO=1 hack/web.sh`; Node 24.2+) boots four demo machines on it under Node and checks addresses, ping, TCP and a DHCP-server handover; the internet comes through a Wisp v1 relay (`?wisp=URL` or the Wisp server field; the library's `Gateway` and `WispClient` in a worker, `www/wisp.js` on the page; `serve.py` has a local one at `/wisp/`, `python3 -m unittest hack/web/test_serve.py` tests it), and `node hack/wasm/wisp.mjs` (after `WEB_DEMO=1 hack/web.sh`) runs `apk update`, `apk add` and a checksummed download in the Alpine demo through it; `cargo clippy --release --target wasm32-unknown-unknown -p uemulator-web` must print zero warnings too
- Guest 3D (M0 of `docs/plans/25-gpu-3d.md`): `?gpu` on the page gives the guest a virgl GPU drawn by a render worker (`www/render.js`, `www/gpu.js`; only clears so far). `hack/gpu/image.py` builds a guest for it into `target/gpu` (Mesa from Alpine edge, kmscube, and `hack/gpu/eglclear.c`, which clears red, green, blue; `hack/web.sh` links it as `gpu/`), and `node hack/wasm/boot.mjs --gpu --kernel target/gpu/vmlinuz-virt --initrd target/gpu/initramfs.gz --disk target/gpu/rootfs.squashfs --memory 1024 --cmdline eglclear.hold=0 --until "EGLCLEAR done"` runs it with the same renderer logging to stderr. Its output must say `GL_RENDERER: virgl`: a guest whose Mesa lacks virgl falls back to llvmpipe and draws through the 2D path
- WebAssembly JIT: `cargo test --release --target wasm32-wasip1 -p uemulator --lib -- --test-threads=1 jit::` runs the differential corpus on the wasm backend under Node (`rustup target add wasm32-wasip1`; the runner is `hack/wasm/test-runner.sh`); run it after touching `jit/wasm*.rs`, `jit/emit_wasm.rs` or `www/jit_host.js`, and `cargo clippy --release --target wasm32-wasip1 -p uemulator --all-targets` must print zero warnings. A panic aborts the whole run (wasm cannot unwind): filter to one module to find the test. `node hack/wasm/boot.mjs --kernel K --initrd I [--disk IMAGE]... [--cdrom ISO]... [--memory MIB] [--firmware none|uefi|bios] [--hypervisor XEN] [--iommu] [--nvram FILE] [--suspend-to FILE] [--resume-from FILE] [--no-jit] [--until TEXT] [--mark TEXT]... [--keys TEXT [--keys-after TEXT]]` boots a real kernel on the built `target/web/uemulator_web.wasm` (`hack/web.sh` first) and times it, `--mark` printing when each text first shows up and `--keys` typing at a boot menu (`docs/plans/13-web.md`; the KDE live ISO measurements in `docs/plans/20-jit-perf.md` round 5)
- Apple app (`docs/plans/28-apple.md`): `apple/uemulator.xcodeproj`, one SwiftUI target (and shared scheme) `uemulator` for macOS and iOS that links `crates/uemulator-apple` (a staticlib with the C ABI in its `include/uemulator.h`) through the `hack/apple/build-core.sh --xcode` build phase; run `WEB_DEMO=1 hack/web.sh` first (the app bundles the Alpine and Xen demos and the firmware), `rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-darwin`, then `xcodebuild -project apple/uemulator.xcodeproj -scheme uemulator -destination 'platform=macOS' -skipPackagePluginValidation build` (or `'generic/platform=iOS Simulator'`; the flag is for SwiftTerm's build plugin, which Xcode asks to trust once). Machines live in the app's `Documents/Machines/` in the CLI's layout (`MachineStore.swift`; `machine.toml` through `ua_machine_load`/`ua_machine_save`, which keep keys the app does not know); `-machine NAME -autostart` boots one, `-new-machine NAME -new-source demo|demo:xen|install:alpine|debian|fedora|iso:FILE|empty` makes one (the installers' URLs are copied from the CLI's `quick.rs` into `apple/App/Presets.swift`: change both), `-debug-log FILE` writes the console to Documents, and `-engine native|webkit` picks the engine: native links the library (JIT on macOS, interpreter on iOS), webkit runs the web build's `worker.js` and wasm JIT in a hidden `WKWebView` driven by `apple/WebEngine/engine.js` over loopback HTTP and a WebSocket (`apple/App/Loopback.swift`; a custom URL scheme gets no SharedArrayBuffer), so a change to `www/worker.js`'s messages or `www/protocol.js` must be mirrored there. `cargo clippy --release --target aarch64-apple-ios -p uemulator-apple --all-targets` must print zero warnings too, and so must the Swift build. `apple/ci_scripts/ci_post_clone.sh` readies an Xcode Cloud machine (Rust, `WEB_DEMO=1 hack/web.sh`, plugin trust); the app icon is `apple/App/uemulator.icon`, drawn from `assets/uemulator-logo.svg`
- UEFI: `./hack/uefi/boot.sh [x86_64|aarch64]` builds `crates/uemulator-uefi` and boots it in QEMU (accelerated when the host matches; `UEFI_ACCEL=hv|emu` picks hardware virtualization or the emulator, and `-cpu max,svm=on` under TCG exercises the SVM path); `cargo clippy --release --target x86_64-unknown-uefi -p uemulator-uefi` (and `aarch64-unknown-uefi`) must print zero warnings too
- Firmware: `--firmware uefi|bios|none` (on `quick create`/`edit` and `advanced boot`), `uefi` by default: the built-in UEFI firmware boots the disk, or the `--kernel`/`--initramfs` it is given (QEMU `-kernel` under OVMF style: the kernel needs an EFI stub, else the boot fails and says to use `--firmware none`; `docs/plans/19-uefi-firmware.md`). `none` enters any bzImage directly in 64-bit mode (what `--verify` and the library's fake-kernel tests use); `bios` boots a disk through the library's BIOS (`MachineConfig::boot_disk`, `docs/plans/17-bios.md`). A `machine.toml` without a `firmware` key is `uefi`
- Disk images: `-- disk create F.udisk --size MIB` (or `--backing BASE`, a path relative to F or an http(s) URL: a copy-on-write overlay), `-- disk convert SRC DST` (raw <-> udisk by DST's extension, flattens overlays), `-- disk info IMAGE`. `--disk` takes raw or udisk and finds an overlay's base itself; new machines get `disk-<n>.udisk`. The format is `docs/spec/uemulator-disk-format.md`; change the spec with the code (`disk/udisk.rs`)
- Display: `--display serial|framebuffer|both` (a screen; `framebuffer` makes it `/dev/console`, `both` keeps the terminal as the console) and `--input[=BOOL]` (virtio keyboard and tablet, by default with the screen) on `quick create`/`edit`/`boot` and `advanced boot`; a machine with either serves the browser viewer at `127.0.0.1:5800` (`--viewer-address HOST:PORT`, or `--viewer-host`/`--viewer-port`; `--viewer-allow-host NAME` for proxies and DNS names; `/screenshot.png` is the screen). The web page has the same choices and a Terminal | Screen switch (`docs/plans/24-display-input.md`)
- Disk boot: `quick boot NAME` boots a machine whose disk has an install on it through the machine's firmware; `--boot-from installer` runs the installer instead (through UEFI for `uefi` machines, with the machine's `nvram.kv`)
- TPM and Secure Boot: `--tpm` adds a TPM 2.0 (CRB at 0xFED40000, ACPI TPM2; the firmware measures the boot and hands Linux the event log; RSA 2048/ECC P-256 keys, sealing, HMAC and policy sessions, NV and persistent objects, enough for systemd-cryptenroll and Linux's `TCG_TPM2_HMAC`; seeds, NV and persistent objects live in the machine's `nvram.kv` under `tpm/`, out of the guest's reach) and `--secure-boot` has the UEFI firmware enforce Secure Boot, enrolling Microsoft's KEK, db and dbx under a uemulator PK into the nvram on first use; both off by default, both on the web page (`?tpm`, `?secure-boot`) and in `hack/wasm/boot.mjs` (`docs/plans/26-tpm-secure-boot.md`). The keys are in `crates/uemulator-firmware/secure-boot/` (provenance in its README)
- Shadow stacks: CET shadow stacks are always offered, as on a Turin (`cpu/cet.rs`); the JIT compiles near call and ret with the shadow-stack push and compare inline on every backend, and the rest runs through the interpreter (`docs/plans/06-jit.md`, "CET shadow stacks"). Old `machine.toml` files with a `shadow_stacks` key load with it ignored
- Hypervisor: `advanced boot --kernel K --initramfs I --hypervisor xen.gz|xen.efi [--hypervisor-cmdline TEXT]` boots Xen through the UEFI firmware with the kernel as dom0 (`MachineConfig::hypervisor`; the console defaults to serial and dom0's to `hvc0`): `xen.gz` by the firmware's Multiboot2 loader, `xen.efi` through Edera's `XEN_EFI_*_MEDIA` media loaders (`docs/plans/18-xen-dom0.md`). `quick create`/`edit` take `--hypervisor` too (the machine keeps a copy in its directory, `--remove-hypervisor` drops it) and run its installer boots under it; an installed disk is refused with it. Edera's Xen: `crane export ghcr.io/edera-dev/xen:4.22 --platform linux/amd64 - | tar x`
- Firmware / real mode: `uemulator advanced boot-firmware --firmware IMAGE` (image ends at 1 MiB, CPU starts in real mode at F000:FFF0); a bzImage without a 64-bit entry boots in 32-bit protected mode (`docs/plans/15-legacy-modes.md`)
- Linux KVM check: `hack/kvm/run.sh` loads `kvm_amd` in the emulated guest and runs vCPUs in every CPU mode on the emulator's SVM (needs `unsquashfs`, a musl cross gcc, the Alpine artifacts and network for the modloop); run it after touching `cpu/svm.rs`, paging or the 16/32-bit modes
- Test: `cargo test --release --workspace` (also `-p uemulator --no-default-features`)
- Snapshots (`docs/plans/29-snapshots.md`): `advanced boot ... --suspend-to FILE` makes Ctrl-] and `--timeout` suspend the whole machine to FILE (disks flushed first); `--resume-from FILE` resumes it with the same options and disks, and deletes FILE once it runs. The format is the same on every host (`hack/wasm/boot.mjs` takes both flags too), so a machine moves between the native and WebAssembly builds. Machine state derives `Snapshot` (`crates/uemulator-snapshot-derive`): a field you add to `Cpu` or a device is saved unless marked `#[snapshot(skip)]`, which host handles, host addresses and caches must be; `machine/suspend/tests.rs` must still pass
- SMP: `--cpus N` gives the guest N vCPUs, each on its own host thread when the host has threads and a clock (`--smp auto`, the default); `--smp timeshare` takes turns on one thread, deterministic on the virtual clock (`docs/plans/22-smp-threads.md`). A freestanding embedder gets threads only through `MachineConfig::thread_spawner` and a `host_clock`
- Before EVERY commit: run `./hack/autofix.sh` (clippy --fix + fmt), then fix by hand every warning it leaves; `cargo clippy --release --all-targets` must print zero warnings. Never commit with warnings.

## Rules

- Cargo workspace: `crates/uemulator-uefi` (`no_std` UEFI app; on hosted targets only its hardware-independent modules build, which is what `cargo test -p uemulator-uefi` runs), `crates/uemulator` (library; `no_std` + `alloc` when `freestanding`; the default `jit` feature pulls in `libc` on unix and `windows-sys` on Windows (and enables the WebAssembly backend on wasm32), `--no-default-features` has no third-party dependencies and is interpreter-only; it always uses `uemulator-crypto`), `crates/uemulator-snapshot-derive` (dependency-free proc macro: `#[derive(Snapshot)]`), `crates/uemulator-cli` (clap, ureq; may use crates freely), `crates/uemulator-virgl` (`no_std` + `alloc`, no dependencies: the host side of virgl for guest 3D, so far the capsets), `crates/uemulator-crypto` (`no_std` + `alloc`, no dependencies: hashes, RSA, X.509, PKCS#7, Authenticode, HMAC, KDFa/KDFe, AES-CFB, P-256, for the TPM and Secure Boot; not constant time), `crates/uemulator-firmware` (the `no_std` UEFI firmware for `x86_64-unknown-none`, which the CLI's `build.rs` builds and embeds; on hosted targets only its hardware-independent modules build, for `cargo test -p uemulator-firmware`) `crates/uemulator-web` (wasm32 only, empty elsewhere; C ABI plus `www/`) and `crates/uemulator-apple` (Apple targets only, empty elsewhere; the C ABI the SwiftUI app in `apple/` links). `cfg(freestanding)` (from `crates/uemulator/build.rs`: UEFI and wasm32 except WASI, which is the hosted test target) replaces `target_os = "uefi"` in the library. Tests live next to the code in each crate; the library's shared helpers are in `crates/uemulator/src/testkit.rs`.
- `lib.rs` is the entire public API: `EmulatedMachine::new(cfg)` then `start()`. Everything else is `pub(crate)`.
- The library never touches stdio, never calls `process::exit`, holds no global mutable state, never panics on guest behavior. Guest faults are guest exceptions.
- Comment what is surprising, looks obscure, or is named something non-obvious: hardware quirks, ordering constraints, invariants the JIT relies on, why a value is what it is. Cite the SDM section or the QEMU behavior when that is the real source. Don't restate what the code says.
- Write comments for the next Claude who has to change this without having seen the history. Say what breaks if the code is changed carelessly. Plain, terse prose like a human maintainer would write: no "This function...", no filler, no banner or section-divider comments.
- Prefer descriptive names. Don't shorten to 3-5 letters when a real word reads better; rename when you touch something badly named. Architectural names from the Intel/AMD manuals (`cr0`, `efer`, `rip`, `gdtr`, `cpl`, `mxcsr`) stay as-is.
- No magic constants. Name register bits, MSR numbers, descriptor flags, vector numbers, sizes and timeouts as `const`s at the narrowest scope that makes sense, and let comments refer to the name.
- `../ext/qemu-uplink` is read-only reference (see `docs/plans/09-qemu-map.md`). Study behavior; write Rust from scratch, don't transliterate.
- The interpreter is the oracle for the JIT. Any new uop gets an interpreter implementation and a test first.
- Advertise a CPUID bit only together with the tests for the instructions behind it.
- JIT blocks are position independent: keyed by physical address, and every guest `rip` a block uses is the page base (`PAGE_BASE`) plus a translation-time offset (`Gen::rip_to`); never embed a guest virtual address in generated code (`docs/plans/06-jit.md`). The code cache is shared by all vCPUs: add or patch code only under its lock, and patch links with `ExecMem::write_word`.
- With threads (`docs/plans/22-smp-threads.md`) RAM and the devices are shared. Take the device lock through `cpu.dev.lock()` for every device access and never hold it into `Cpu::with_exclusive` (the others may be waiting for it). Guest memory goes through `mem_read`/`mem_write` (acquire/release, atomics), not through slices, whenever another vCPU could be writing it. Anything machine-wide you add to `Cpu` needs a decision twice: `swap_shared` for time-sharing, and shared handle or private copy for threads.
- Debug-profile is optimized (`opt-level = 3`) because the kernel decompressor is ~1e9 guest instructions.

## Tests

- Unit tests only: no network, no cached kernels or initrds, nothing under `~/.uemulator`. A test that needs a guest builds a tiny one: `testkit::FakeKernel` makes a valid bzImage whose 64-bit entry point is hand-assembled code (`echo 'mov rax, 5; hlt' | hack/asm.sh` prints the bytes; `BITS=16` or `BITS=32` assembles for real mode or 32-bit protected mode).
- `testkit::Harness` runs a snippet on one CPU, interpreter or JIT, with undelivered faults reported as `Stop::Fault`; `testkit::run_machine` boots a fake kernel on a full `EmulatedMachine`.
- Anything the JIT compiles gets a case that runs `testkit::assert_jit_matches_interpreter`. The interpreter is the oracle. The same corpus runs on the WebAssembly backend (above), so a form the wasm generator lowers needs no case of its own beyond a differential run there.
- Fixing a bug: write the failing test first.
- Threaded tests (`testkit::run_threads`, `machine/tests.rs` with `SmpMode::Threads`) are the ones that catch memory-ordering and atomicity bugs, and only on a native aarch64 host (Rosetta runs x86 with hardware TSO). When you change the atomics or the ordering, remove the thing under test and watch the test fail before trusting it.
- Under Rosetta (`--target x86_64-apple-darwin`) tests that run generated code take turns through `jit::serialize_jit_tests`; Rosetta's translation cache goes stale when one thread frees a code buffer and another maps one at the same address. `testkit::Harness::enable_jit` holds it for you; take it yourself when you use `Jit::new` directly.
- Real-kernel lockstep check (not a test, needs a kernel you supply): `--verify` on the CLI.
- Real boot loader check (not a test, needs a disk an installer wrote): `quick boot NAME --realtime` on an installed Alpine machine with `--firmware bios` (new machines are `uefi`); run it after touching `cpu/bios.rs`.

## Debugging

- `--debug` on the CLI dumps CPU state and scans guest RAM for the kernel log ring buffer on exit.
- `--verify` runs the JIT in lockstep with the interpreter and stops at the first diverging block; use it after any change under `crates/uemulator/src/jit/`. Do not type into it: host input reaches only the JIT side's console, so the first keystroke shows up as a bogus divergence at an interrupt entry (boot to the shell prompt and stop instead).
- `--time <unix>` fixes the RTC; guest behavior must not depend on it, so a time-dependent failure is an emulator bug.
- On an Apple Silicon Mac the x86_64 JIT runs under Rosetta: `cargo test --release -p uemulator --target x86_64-apple-darwin` (`rustup target add x86_64-apple-darwin`).
