# Apple platforms: a SwiftUI app

**Status:** proposal. M0, the spike that decides whether the WebKit engine is worth building, is done ("M0 results" below: it is, served from loopback HTTP rather than a scheme handler). M1 to M5 are built: `apple/uemulator.xcodeproj` boots the Alpine demo on the native engine (JIT on macOS, interpreted on iOS) and on the WebKit engine (the web build's wasm JIT in a hidden web view, on both), with a screen, keyboard and pointer, from the demo or an ISO, as named machines whose disks keep what the guest wrote, with the internet through the app on both engines.

A native app for macOS, iOS and iPadOS (visionOS later, tvOS only interpreted) that does what the web page does (`13-web.md`): pick or create a machine, boot it, show the terminal or the screen, type into it, network it. The UI is SwiftUI throughout. No web page is ever shown.

## Why there are two engines

Apple's platforms split on one question: may the app map executable memory?

- **macOS: yes.** A hardened-runtime app with `com.apple.security.cs.allow-jit` gets `MAP_JIT`, which is what `sys.rs` already uses on Apple Silicon (and `pthread_jit_write_protect_np` for the W^X switch). The library links into the app and runs exactly as under the CLI: aarch64 JIT (x86_64 JIT on Intel Macs), one host thread per vCPU, no 4 GiB cap. WebAssembly would only make the Mac slower.
- **iOS, iPadOS, visionOS, tvOS: no.** An App Store app has no `dynamic-codesigning` entitlement. `mmap(MAP_JIT)` fails, so `Jit::new`'s probe falls back to the interpreter. Embedding a WebAssembly runtime with its own compiler (wasmtime, wasm3's AOT, ...) does not help: it needs the same executable memory. An in-process `JSContext` has no JIT on iOS either; it would interpret the WebAssembly, which is slower than interpreting x86 natively. The EU browser-engine entitlement is only for browsers, and the debugger-attached JIT tricks are not shippable.

The one process on iOS that may JIT is WebKit's WebContent process, which compiles WebAssembly (BBQ, then OMG) for any `WKWebView`. The library already has a backend that emits WebAssembly (`jit/wasm.rs`, `jit/emit_wasm.rs`) and a host for it (`www/jit_host.js`). On V8 that backend boots a Debian netboot kernel in about 6 s against 55 s interpreted (`13-web.md`, "Tests").

So "JIT through WebAssembly" means:

| engine | where the emulator runs | JIT | platforms |
|---|---|---|---|
| `NativeEngine` | in the app process: the library as a static library | aarch64 / x86_64 where `MAP_JIT` works, else the interpreter | macOS (JIT); iOS, iPadOS, visionOS, tvOS (interpreter) |
| `WebKitEngine` | in a hidden `WKWebView`'s WebContent process: the existing `uemulator_web.wasm` | the WebAssembly backend, compiled by JavaScriptCore | iOS, iPadOS, visionOS (macOS too, for testing) |

The thing to understand about `WebKitEngine`: a JIT block is a wasm module that imports the emulator's `memory` and `table` (`13-web.md`, "The JIT"). It reads guest RAM and the `Cpu` directly in that linear memory. Native Rust code in the app cannot share that memory, because it lives in another process. So the WebAssembly build is not a JIT plugged into a native core. **The whole core runs inside WebKit, and Swift is a remote UI** that exchanges bytes with it. The web view is never on screen; it only executes code. The emulator side is the web port with its page replaced by a headless shim.

On iOS the user picks the engine per machine. The default is `WebKitEngine` when M0 shows it beats the native interpreter, which it should by a wide margin. The native interpreter stays as the engine that always works: no WebContent memory ceiling, real threads for SMP, no 3 GiB RAM cap.

## Layout

```
apple/
  uemulator.xcodeproj           committed, hand-written; one multiplatform target and shared scheme, `uemulator`
  App/                          SwiftUI and the engines: UemulatorApp, MachineStore, MachineView,
                                MachineSettingsView, NativeEngine, WebKitEngine, Loopback, Wisp;
                                uemulator.icon (the Icon Composer app icon) and the macOS entitlements
  WebEngine/                    the WebKit engine's page: engine.html, engine.js (drives www/worker.js)
  ci_scripts/ci_post_clone.sh   Xcode Cloud's setup: Rust, the web build, plugin trust ("Xcode Cloud")
crates/uemulator-apple/         staticlib with a C ABI for NativeEngine
hack/apple/build-core.sh        cargo for the build phase, or every slice into UemulatorCore.xcframework
hack/apple/bundle-app.sh        copies the firmware, the web build and the Alpine demo into the app
assets/uemulator-logo.svg       the logo the app icon is drawn from
```

The layout planned before M1 had a separate `UemulatorKit` package and test target; the engines stayed in `App/` instead.

- `crates/uemulator-apple` mirrors `uemulator-web`'s C ABI on purpose: `ua_create(config) -> handle`, `ua_add_disk`, `ua_set_firmware`, `ua_start`, `ua_stop`, plus callbacks that match the web host imports one for one (`output`, `input`, `frame_ready`/`frame`, `cursor`, `input_events`, `net_recv`/`net_send`, `wisp_*`, `log`). With both engines on the same event vocabulary, `MachineEngine` is one Swift protocol and the UI never knows which engine it has. The header is handwritten (no cbindgen, keeping the crate's dependencies to the library's), and it is the only thing outside `lib.rs` that sees the library: it uses the public `EmulatedMachine` API like the CLI does, and `lib.rs` stays the entire public API.
- The xcframework has slices for `aarch64-apple-darwin` + `x86_64-apple-darwin` (lipo'd), `aarch64-apple-ios`, `aarch64-apple-ios-sim`, and later `aarch64-apple-visionos[-sim]` / `aarch64-apple-tvos` (tier 3: `-Zbuild-std`). An Xcode "Run Script" build phase calls `hack/apple/build-core.sh` with `$PLATFORM_NAME` and `$CONFIGURATION`, so a plain ⌘B builds the Rust. Xcode Cloud builds it all through the shared scheme `uemulator` ("Xcode Cloud" below).
- Bundled resources: `uemulator_web.wasm` and the shim (iOS/visionOS), `uemulator-firmware.bin` (both engines; the CLI embeds it through `build.rs`, and the app loads it as a resource instead), and the Secure Boot keys the firmware needs.
- Warnings: `cargo clippy --release --target aarch64-apple-ios -p uemulator-apple` must print zero, like the other targets, and the Swift side builds with warnings as errors.

## WebKitEngine

A `WKWebView` that sits in the view hierarchy, 1×1 with opacity 0 (M0 boots in it like that). It loads `http://127.0.0.1:<port>/<token>/engine.html` from a small HTTP server the app runs on loopback (`NWListener`), which serves the bundle and the app's files. Not a `WKURLSchemeHandler`: see the next paragraph. The shim is `www/worker.js` and `www/jit_host.js` almost unchanged. `main.js`, xterm.js and every piece of UI are dropped.

**Cross-origin isolation.** `uw_run` blocks a Worker, and the page talks to it through `SharedArrayBuffer` rings (`www/protocol.js`). WebKit grants `SharedArrayBuffer` only to a cross-origin-isolated page, so every response carries `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, as `hack/web/serve.py` sends. M0 found that a custom scheme is not enough: on `uemulator://` the page reports `crossOriginIsolated === true` and still has no `SharedArrayBuffer` constructor and no shared wasm memory, also after a first navigation to a page without the headers (which should have forced a process swap). WebKit only enables them in a WebContent process it started for a COOP navigation, and evidently not for custom schemes. The same headers from `http://127.0.0.1` work: `127.0.0.1` is a secure context, and ATS lets loopback through without an exception. The server listens on 127.0.0.1 only. Other apps can still reach a loopback port, so every path starts with a random per-launch token, and anything else gets a 404.

**The bridge.** Everything the page did with UI now crosses a process boundary:

- Disk reads: the worker already reads disks with synchronous range XHRs (`host_disk_read`, `rangeRequest`). Those go to `/<token>/disk/<id>` on the loopback server, which answers them from the file with `FileHandle` reads (M0: a 512-byte range read from a worker works). Nothing new is needed, and big ISOs never load into memory.
- Disk writes: today they land in an in-memory udisk overlay that dies with the page. For a persistent disk, add a `host_disk_write` import: a synchronous `POST /<token>/disk/<id>?offset=` whose body the server writes to the udisk file. M0: a worker's synchronous 1 MiB POST arrives whole in 6 to 11 ms, on both transports.
- Console, screen, input, network and Wisp: one binary stream each way between the page's main thread and the app. The page's main thread drains the worker's rings as `main.js` does today and forwards the bytes; going the other way, it fills the input, net and Wisp rings. Two candidate transports, measured in M0 (a 3 MiB frame, round trip, one in flight):
  1. `WKScriptMessageHandlerWithReply` / `callAsyncJavaScript`. Simple, but its values are property lists (no `ArrayBuffer`), so bytes travel as base64 strings: 31 to 34 ms a frame.
  2. A WebSocket from the page to an `NWListener` on loopback in the app. Binary frames, no base64; same listener and token as the HTTP server: 5.2 to 5.9 ms a frame (about 550 MB/s), 6× faster. **This is the transport.**

  The screen is the heavy one: a 1024×768 frame is 3 MiB, 180 MiB/s at 60 Hz. Only the damaged rectangles cross (virtio-gpu flushes come with rects; `host_frame` takes a rect), at most once per display refresh. The app acknowledges each frame the way the page does (`FRAME_ACK`), so a slow bridge drops frames instead of queueing them.
- Network: the guest's NIC stays on the library's `Gateway` + `WispClient`, which run inside the wasm (`27-wisp.md`). The app is the Wisp v1 relay: a small Swift server for the protocol (TCP and UDP streams over `Network.framework`) on the same stream. No external relay, no browser networking. `NativeEngine` uses the library's gateway directly, as the CLI does.
- Lifetime: WebKit can kill WebContent under memory pressure (`webViewWebContentProcessDidTerminate`). The engine reports it as the machine stopping with an error, never as a crash. Guest RAM counts against the WebContent process's jetsam limit, so the RAM picker on this engine is capped by what M0 measures on the smallest supported device (and never above the wasm32 3 GiB in any case).

**What the WebAssembly JIT loses on JavaScriptCore.** Measured in M0 (simulator):

- The compile worker relies on V8's process-wide native module cache (`jit_compiler.js`). JSC has no measured equivalent, so the page already skips it outside V8 (`compileWorkerHelps`), and blocks compile on the emulator's thread. The boot ("M0 results") is 1.4× slower than V8 without its compile worker and 1.9× slower than V8 with it, and module creation is the first place to look: 26k one-block modules, all compiled on the emulator's thread. Batching blocks into modules without the worker (the batching exists, gated on the queue), or a JSC-specific compile worker if JSC shares compiled code, is the first JIT work for this engine.
- Tail calls chain blocks (`return_call_indirect`). Without them the chain stub fails to compile and the JIT runs unchained. That is correct but slower. JSC validates `return_call` and `return_call_indirect` (and fixed-width SIMD) in the simulator's WebKit, so the chained JIT runs there. On a device it does not: see "WebKitEngine on devices", and the app runs devices unchained.
- Fixed-width SIMD (`probe_simd`) is probed already and works either way.
- SMP: the WebAssembly JIT runs all vCPUs on one thread (`13-web.md`, "The JIT"). A machine that needs real parallelism belongs on `NativeEngine`.

## NativeEngine

`ua_start` spawns the machine through the library's normal hosted path (`std`, threads, `SmpMode::Threads`). Callbacks fire on the emulator threads, and Swift hops them to the main actor in batches (console every 16 ms like `worker.js`; frames on `CADisplayLink`/`CVDisplayLink`). On iOS, iPadOS, tvOS and visionOS `ExecMem::new` refuses without mapping anything (`sys.rs`), the probe fails, and `ua_create` builds the machine again interpreted. Calling into a mapping to find out is not safe there ("WebKitEngine on devices"). The engine reports "interpreted" so the UI can say so.

There is no scheme handler on this engine: disks are opened directly through the library's own file-backed raw/udisk code, the same as the CLI.

## The SwiftUI app

It follows the web page's structure (`13-web.md`, "The page") so the two stay recognizable:

- **Machine list** (sidebar / `NavigationSplitView`): named machines stored the same way the CLI does (`machine.toml`, `artifacts/`, `disk-<n>.udisk`, `nvram.kv`) under the app container's `Machines/`. On macOS a user-granted folder bookmark can point it at `~/.uemulator/machines`, so the CLI and the app share machines. Parsing `machine.toml` stays in Rust (`ua_machine_load`) so the two never disagree about the format.
- **Presets and settings:** the web page's presets (live CD/installer ISO, disk image, kernel to a shell, the Alpine demo), and the same choices: firmware (`uefi`/`bios`/`none`), memory, vCPUs, drives (Files app / `fileImporter`, drag and drop on macOS and iPad, URLs downloaded into the machine), kernel/initramfs/command line, display/console, network on/off, TPM, Secure Boot, hypervisor (Xen). The same warnings the page shows before Start. Those checks should move out of `main.js` into Rust shared by both (`ua_validate`), or the web page and app drift apart.
- **Run view:** a state chip (Running + uptime, Starting, Stopped, error) and Terminal | Screen.
  - Terminal: SwiftTerm (MIT, VT100/xterm, macOS and iOS views). Bytes in from `output`, keystrokes out through `input`, size changes through `resize`. On iOS, an accessory bar for Esc, Ctrl, Tab and arrows.
  - Screen: a `MTKView` (or a `CALayer` fed `IOSurface`s) that uploads damaged rects into a texture, aspect-fit, with "resize guest to fit". Keyboard input becomes evdev codes for virtio-input: `NSEvent.keyCode` on macOS, `UIKey.keyCode` (HID usages) from `pressesBegan` on iPad hardware keyboards. Pointer, trackpad and touch become absolute tablet events, and the guest cursor (`host_cursor`) is drawn as a hardware cursor where the platform allows. Ctrl+Alt+Del is a toolbar button.
- **Network:** the shared Ethernet segment between machines (`SegmentAgent`) maps to "machines in this app share a segment", with the app forwarding frames between running engines. Internet goes through the in-app Wisp relay above, or the native gateway.

## The UI as it is (2026-11-15)

The machine menu of M3 and M4 is gone; what it held is in a settings sheet. Later sections describe it as it was then.

- Library: a split view (a pushed list on a phone) under the logo (and the name on a Mac). Each row shows screen or terminal, a green dot while running, and what it runs and its memory; its context menu (in `MachineRow`, which observes the machine, so Delete is enabled the moment it stops) has Start/Stop and Delete. Nothing is made on first launch: an empty library offers a small Try a Demo menu.
- New machine (+): Install, Custom, then Demo as a submenu. Demo (Alpine Linux, Edera Xen: 1 GiB, a NIC, `uemulator.host=app` on the command line so the demo's welcome says it runs in the app; Xen's arguments and IOMMU come from the bundled `demo.json`), Install (Alpine, Debian, Fedora: the CLI's `quick create --install`, `Presets.swift` copying `quick.rs`; 2 GiB, Fedora 3 for its stage2, a 64 GiB udisk, a NIC; `install` and `boot_from = "auto"` in `machine.toml`, the netboot kernel and initramfs downloaded on first start under the CLI's names), both made and started at once, and Custom (an ISO, a disk image, a kernel and initrd, each copied into the machine's folder; memory, a new disk, display, network). `auto` boots the installer until `ua_disk_installed` sees data in the first disk's first 32 KiB, as the CLI does. A guest reset ends the run (no `OPTION_REBOOT`) and the app starts the machine again, so it decides afresh what boots.
- Full screen (the toolbar, ⌃⌘F): no sidebar, no bars, the status bar hidden (set on the root split view: iOS ignores it from the detail), the screen or terminal edge to edge, and the keyboard and exit buttons at the bottom inside the safe area; a Mac's window goes full screen with it.
- Keyboard bar (iOS): the software keyboard has SwiftTerm's accessory bar rebuilt for keys (`KeyAccessory`): esc, a sticky ctrl, tab, ~ | / - and F1 to F12 in a strip that scrolls, the arrows and hide. On the screen a key goes down on touch and up on release, so the guest repeats a held arrow itself; the terminal uses the same bar (`TerminalSession` turns its keys into terminal bytes and repeats a held arrow), because SwiftTerm's own bar's keyboard key swaps the keyboard for SwiftTerm's key grid instead of hiding it. Installer machines are made with Screen and terminal, the demos with the terminal only. Unfolded, the keyboard and its bar push the guest up rather than cover it: the screen is drawn in the part above them (`ScreenUIView.contentRect`, following `keyboardLayoutGuide`), and the terminal's bottom is pinned to the keyboard's top while it has the keyboard (`TerminalContainer`), so its rows shrink and the guest sees the new size. Folded, neither moves: the keyboard is below the fold.
- Folded (iOS, `FoldedLayout.swift`): a foldable partially open in portrait (`UIHingeInteraction` says `partiallyOpen`, iOS 27.1) splits the machine's view at the fold, taken to be the middle of the screen since UIHinge gives no position: the screen or terminal above it, and below it `FoldedControls`: the Terminal | Screen switch, the keyboard toggle (the screen's software keyboard or SwiftTerm's), Resize to Fit (the part above the fold), Full Screen, and a Tap to Type area the keyboard comes up into. The guest stops `FoldPosture.clearance` above the fold and the panel starts as far below it. The key bar is not on the keyboard while folded: the keyboard and an accessory together are taller than the lower half, so it crossed the fold. The screen and the terminal each have a second, freestanding bar (`KeyAccessory(freestanding:)`, dark and full width) that `FoldedControls` shows just below the fold, outside the part the keyboard clips; a second bar rather than moving the first, since UIKit takes an accessory back out of whatever holds it when the input views reload. Leaving Screen puts its keyboard down. Folding upright enters full screen and folding flat (or turning sideways) leaves the full screen that folding entered. The bottom bar is hidden while folded. Full screen makes the top half all guest, and the panel adds the state chip, Settings and Start/Stop the hidden navigation bar had. Fully open, landscape and devices without a hinge keep the usual layout. `-fold-posture partial` fakes the posture (the simulator's iPhone Duo has no hinge to bend).
- Machine: the toolbar has the state chip (on iOS an info button in the top bar instead, `MachineInfoButton`: green while running, orange after a failure, and a popover with the chip, the engine and the machine's summary), the Terminal | Screen switch, Resize to Fit (screen only, while running), the iOS keyboard toggle, Settings and Start/Stop. Until a machine first starts after launch, the detail shows its summary with Settings and Start instead of a black terminal; why the last start failed shows there too.
- Settings (`MachineSettingsView.swift`): an edited copy of the definition, saved on Done, applied at the next start; picked files are imported on Done. Memory (to 3 GiB on the WebKit engine), processors, display, network; the engine (fixed while running: the engine object is the running machine); Boot From for an installer machine; disks (Add: an ISO, a disk image, or a new `disk-<n>.udisk`; Detach keeps the file); TPM and Secure Boot; Advanced: firmware (UEFI, BIOS, none), kernel and initrd, the command line (added to, or replacing, the default), a hypervisor and its command line, the console, JIT, IOMMU, SMT, one thread for all processors (native), the RNG, restart on reboot; Delete. Every key is the CLI's; the CLI opens an installer machine the app made (`quick show` and `boot`), not a demo or custom one, which have no `install` key.
- `ua_config` covers the library's `MachineConfig` but for what means nothing to the app (GPU, thread spawner, entropy and poll hooks): the web build's option bits (IOMMU, reboot, replace command line, debug, no SMT) at the same numbers, `UA_OPTION_TIMESHARE`, the firmware kind, a hypervisor and its command line, a fixed RTC time, the display size and a log callback. New fields go at the end; `lib.rs` asserts the layout the header describes.

## Xcode Cloud (2026-11-15)

`apple/ci_scripts/ci_post_clone.sh` readies a fresh Xcode Cloud machine, which has Xcode and nothing else: rustup (stable, minimal) with every target `build-core.sh` can be asked for (both macOS architectures for an archive, iOS, both simulator architectures, the firmware's `x86_64-unknown-none`, the web build's `wasm32-unknown-unknown`), then `WEB_DEMO=1 hack/web.sh`, which downloads Alpine and Xen every build since nothing is cached between builds. It also sets the Xcode default that trusts package build plugins, since Xcode Cloud takes no `-skipPackagePluginValidation`. It touches that default only when `CI_PRIMARY_REPOSITORY_PATH` is set, so running it by hand changes nothing in the local Xcode. The workflow builds the shared scheme `uemulator`. Signing is Xcode Cloud's: the project has no `DEVELOPMENT_TEAM`, and macOS signs ad hoc (`CODE_SIGN_IDENTITY[sdk=macosx*] = "-"`) for local runs, which an archive for TestFlight or the App Store has to replace.

## Suspend and resume (2026-11-16)

`29-snapshots.md` has the library side; this is the app's. A machine's snapshot is `suspended.snapshot` in its folder, with `suspended.json` recording its disks' names, sizes and modification times.

- `MachineEngine.suspend()`: `NativeEngine` calls `ua_suspend`. `WebKitEngine` sends the page `suspend`, `engine.js` stores `STOP.SUSPEND`, and the worker writes the snapshot through the loopback server (`LoopbackFiles.registerSnapshotSink`: by offset into `.tmp`, `finish=1` renames). Both report `.preparing("Suspending")`, then `.stopped("Suspended")` once it is complete. A WebKit page that is reconnecting gets the request when it is back.
- Start resumes when a snapshot exists and its record matches the disks (`MachineStore.snapshotMatches`); otherwise the snapshot is set aside and the machine boots afresh, saying why. The engine deletes the snapshot once the guest runs. A failed resume (settings changed since) keeps it and says to put the settings back or discard it.
- iOS: `MachineModel` suspends a running machine when the app enters the background (with a background task while it writes) and starts it, which resumes it, when the app comes back. If iOS ended the app meanwhile, the machine shows Resume. macOS suspends only on request.
- UI: Suspend (⇧⌘S) in the toolbar while running; Start reads Resume when there is a snapshot; Settings has Discard Suspended State. Changing the engine in Settings while suspended moves the machine to the other engine.
- `-debug-suspend-after SECONDS` suspends each run that long after it starts, for scripted checks with `-autostart`.
- Not yet checked in the app itself (`29-snapshots.md`, "Checked"); the library, the CLI and the WebAssembly build were.

## NVRAM on both engines (2026-11-16)

A machine keeps its UEFI variables (boot entries, Secure Boot keys) and TPM state in its `nvram.kv` on either engine, so moving it between them (Settings, while stopped) loses nothing: before, a machine moved to the WebKit engine lost its boot entries and, worse, its TPM seeds, so a LUKS key sealed with `systemd-cryptenroll` would no longer unseal.

- Library: the key-value log is `LogKeyValueStore<L: KeyValueLog>`, freestanding; `FileKeyValueStore` is it over a file. The web build's `uw_set_nvram` gives it a log on the host (`docs/plans/13-web.md`).
- App: `WebKitEngine` registers the machine's `nvram.kv` with `LoopbackFiles.registerKeyValueLog`, and the boot message names it; `engine.js` passes it to `worker.js`, which reads it whole at the start and POSTs `?offset=N` (a write, synchronized before the 200) or `?replace=1` (the whole log through `nvram.kv.tmp` and a rename, as `FileKeyValueStore` replaces it) for each change. The file is opened per request: a handle kept across a replacement would write into the unlinked old file.
- Checked: under Node (`hack/wasm/boot.mjs --nvram`), the Alpine demo through UEFI with a TPM wrote `tpm/state`, kept it across a second boot, and the CLI's native `advanced boot-uefi --nvram --tpm` on the same file kept the same TPM state and added `Boot0000`/`BootOrder`, which the web build then kept; a file in another format is refused and left as it was. `LoopbackFiles`'s side (missing log, write, retried write, replace, end of run) with a small harness linking `Loopback.swift`. Not checked: the app itself, whose scripted launch on the Mac came up without a window (as noted in "M4 as built"), and the simulator, which this host's CoreSimulator was too old to run.

## WebKitEngine on devices (2026-11-15)

The first runs on a real device (an iPad Pro 12.9" 6th generation, M2, iPadOS 27.2.1, a Debug build installed by Xcode) found two crashes the simulator never showed.

- `NativeEngine` died in `ua_create`: SIGBUS, KERN_PROTECTION_FAILURE with the PC at the fault address. The RWX `mmap` (no `MAP_JIT` off macOS) succeeded, the pages were not executable, and `jit_probe` called its `ret` there. A probe cannot catch that without a signal handler, which the library may not install, so `ExecMem::new` now refuses on every Apple OS but macOS. The engine then runs interpreted, as planned.
- `WebKitEngine` lost its WebContent process (`WebPageProxy::processDidTerminate: reason=Crash`; no crash report is written) ~100 ms after the page loaded, before the firmware printed. With the JIT off it booted. A dump of the modules the JIT handed `host_jit_compile` showed the probe, both chain stubs and the SIMD probe compiled, and the crash came with the first block, the first code that tail-calls into a stub. Refusing just the two stubs (what an engine without tail calls does) made the chip say `wasm` and the Alpine demo reach its shell. So JSC on the device validates and compiles `return_call_indirect` and dies running it. That cannot be probed for either: the app sends `jitChaining: false` in the boot message on every device but macOS (`WebKitEngine.jitChaining`), and `worker.js` hands it to `jit_host.js`, whose `host_jit_chaining` import `Jit::new` checks before compiling the stubs. The simulator and macOS stay chained.

Not checked: whether an iPhone (A-series) or another iPadOS version does the same, which instruction pattern in the stubs JSC trips on, and how much slower the unchained boot is on the device. Mobile Safari uses the same JSC, so the web page turns chaining off in Safari outside macOS (`jit_host.js`'s `chainingWorks`, by user agent and touch points, since iPadOS Safari calls itself a Mac); that cannot tell a device from the simulator, so the simulator's Safari runs unchained too. Not checked on a device's Safari.

## Backgrounding (2026-11-15)

An install on an iPad with the WebKit engine died when the app went to the background; on return the machine was gone. What the code did then, any of which ends a run:

- `engine.js` ended the worker the moment its bridge WebSocket closed (`stop()` then `worker.terminate()` in the same turn), so `uw_run` never returned and the udisk map updates the guest had not flushed were lost. iOS may take a suspended app's sockets away, listening ones included (TN2277), and the bridge is one.
- The loopback listeners never noticed failing: `port()` handed out the old port, nothing listened there, and the worker's synchronous disk requests failed, which the guest sees as I/O errors.
- The app never noticed the bridge closing (`BridgeSocket.receiveLoop` returned quietly), so the chip said running over a dead machine.
- A WebContent process that iOS ends for memory was already reported (`webViewWebContentProcessDidTerminate`), without saying the background was why.

Now:

- `LoopbackListener` restarts a failed listener on the port it had (a running page has its ports baked in: the disk URLs, the bridge's and Wisp's addresses), and `revive()` replaces one that is not ready when the app returns to the foreground.
- `worker.js`'s synchronous disk requests (`sendSync`) retry for up to 20 s while the server cannot be reached (status 0 or a thrown network error; an answered error is never retried), so the guest's request waits instead of failing; only for disks the engine page marks `retryUnreachable`, so the web page's URL disks still fail at once.
- `engine.js` reconnects a closed bridge with the same token and run, gives up only after 60 attempts with no word from the app, and then stops the worker and waits up to 5 s for its exit before terminating it. Console output made while disconnected is held (up to 1 MiB) and sent on reconnecting. The app answers a reconnect with `reattached` (the page asks for a whole frame, since the ack in flight was lost) and the terminal size; a reconnecting page of a stopping run gets `stop` again.
- `WebKitEngine` gives a page whose socket closed 20 s in the foreground to come back, then stops the run saying so (the page itself keeps trying for about a minute, so the app gives up first); it starts a background task when the app goes to the background, so the app and its servers keep running through the grace iOS gives (about 30 s; the WebContent process may be suspended sooner, at WebKit's discretion), and at its end synchronizes the writable disks and lets the app be suspended. Stopping the machine instead would end an install just as surely. A WebContent process that ends in the background, or within 10 s of returning, is reported as "iOS ended the machine while the app was in the background".

What iOS does not allow: running on after the grace period. Only audio, VoIP, location and similar background modes keep an app running, and claiming one to run an emulator would not pass App Store review. So a suspended machine is frozen (guest time jumps when it resumes, as after a host sleep), and if iOS ends the WebContent process while the app is suspended (it does under memory pressure, and a machine with 2 GiB of RAM is a big target) the machine is gone and its disks hold what the guest last flushed, as after a power cut: Linux's journal commits flush every few seconds, so the filesystem survives but an install in progress has to start over. Guest TCP connections through Wisp are lost too (`wisp.js` reconnects; an installer may have to retry a download). The native engine runs in the app's own process with direct file I/O and no loopback sockets, so it freezes and resumes with the app and is only lost when the whole app is; it is the robust choice for a long install, at the interpreter's speed.

Checked on the iPhone 18 Pro simulator (iOS 27.2), WebKit engine, Alpine demo:

- `-debug-drop-sockets SECONDS` (Debug builds: that long after the machine starts, every loopback listener fails and the bridge drops, as a reclaim would). At 8 s the page reconnected within a second, the guest booted on to its shell, keys typed afterwards reached it, and `apk update` ran through the restarted Wisp listener. At 45 s, with a 64 MiB udisk attached and a loop of 40 `dd ... of=/dev/vda bs=64k count=16 conv=fsync` running across the drop: every write succeeded, `dmesg` had no errors, and after the app was killed `disk info` read the image cleanly with the 3.4 MiB written.
- Home with a once-a-second loop in the guest, 50 s away, then back: the background task's expiration handler ran 27 s in and ended it (no warning), but the simulator suspended nothing: the guest ticked the whole time and nothing reconnected. The simulator cannot show what a device does on suspension.
- Home, then the WebContent process killed (`kill -9`, standing in for jetsam), then back: the machine stopped with "iOS ended the machine while the app was in the background".

Not checked on a device: whether WebKit suspends the WebContent process before the app's grace period ends, whether iOS actually takes the loopback sockets during a short suspension, and whether the restarted listener gets its port back every time. `revive()` trusts a listener that still says it is ready; one that iOS took without a state change would only be replaced once it fails.

## Installing Alpine (2026-11-15)

## M5 as built (2026-11-15)

- One Wisp v1 server in the app (`apple/App/Wisp.swift`), Network.framework connections for the guest's TCP and UDP streams, modelled on `hack/web/serve.py`'s, which the library's client is tested against: CONTINUE on stream 0 with 128 packets of credit, a TCP stream's credit back after every 64 DATA packets its destination took, DATA that comes before the connection is ready kept for it in order, a client's CLOSE graceful (queued data, then a FIN), a destination's end or failure reported with the reason (DNS failure 0x42, refused 0x44, timed out or no answer within 10 s 0x43, anything else 0x03). `WispSession` knows nothing about its transport.
- WebKit engine: the worker's own `Gateway` and `WispClient`, as on the web page; the page (`engine.js`) holds the segment's server role (it is the only machine on its BroadcastChannel, so it answers DHCP), and connects `www/wisp.js`'s `connectWisp` to `WispSocketServer`, a loopback WebSocket listener. The server cannot see a WebSocket's URL path, so the page offers the launch token as its subprotocol (`connectWisp` gained an optional `protocols` for this; the web page offers none) and any other upgrade is refused.
- Native engine: `crates/uemulator-apple/src/network.rs` pumps the library's `Gateway` (policy `UserNet`: it answers DHCP for 10.0.2.15 itself, and 10.0.2.3:53 goes to 1.1.1.1) and a `WispClient` on a thread, in the `WispClient` contract's order, woken by the NIC's guest-frame hook and by the server's messages. Its packets come to Swift through `ua_network_start`'s callback and go to a `WispSession` in process; the session's answers go back through `ua_wisp_connecting`/`ua_wisp_message`/`ua_wisp_lost`. `UA_OPTION_NETWORK` is the app's own bit (1 << 16), clear of the web build's. Stopping detaches the session before `ua_destroy`, which stops the pump before the machine goes, so no packet crosses either way after a stop (a unit test holds the latter).
- A machine's network is the CLI's `[[networks]]`: on is any entry, and an entry the CLI wrote is kept as it is; a new one is `{model = "virtio", link = "user"}`, what `quick create` writes. New machines get one; the machine menu toggles it.
- Checked on the iPhone simulator with the Alpine demo: DHCP gave 10.0.2.15, `apk update` fetched both repository indexes, on the WebKit engine and on the native engine (interpreted); on WebKit `apk add curl` worked and curl in the guest fetched `main/x86_64/APKINDEX.tar.gz` with exactly the bytes the Mac's own curl got (528,446).
- Not done: the segment between the app's machines (each WebKit engine has its own origin, so its own BroadcastChannel; the native engine has no segment at all), inbound connections, and a real device.

## M4 as built (2026-11-15)

- `MachineStore` (`apple/App/MachineStore.swift`): machines in the app's `Documents/Machines/<name>/`, in the CLI's layout: `machine.toml`, `disk-<n>.udisk`, `nvram.kv`, `artifacts/`. `machine.toml` goes through Rust (`crates/uemulator-apple/src/machine_file.rs`: `ua_machine_load` gives JSON, `ua_machine_save` merges JSON into the TOML table and writes it atomically), so every key the app does not use survives it; tested against a machine file the CLI wrote. The app uses `memory`, `cpus`, `firmware`, `display` (the CLI's `serial|framebuffer|both`), `consoles`, `tpm`, `secure_boot`, `append` and `disks`. What only the app knows goes in a sidecar `app.json` (the engine, the CD as a security-scoped bookmark, or a file in Documents): the CLI drops keys it does not know when it saves, so they cannot live in `machine.toml`. Disk paths are absolute, as the CLI writes them; an iOS container moves when the app is reinstalled, so a missing disk is found by name in the machine's folder (it did, across three reinstalls in testing). App-made machines have no `install` key, which the CLI requires, so the CLI cannot open them yet.
- New disks: `ua_disk_create` makes a sparse udisk (the id from `/dev/urandom`), as `uemulator disk create` does; it never replaces a file.
- Native engine: writable disks are the files themselves; `ua_config.nvram_path` gives each machine its `nvram.kv` (`FileKeyValueStore`), and `UA_OPTION_TPM` / `UA_OPTION_SECURE_BOOT` turn on what keeps its state there.
- WebKit engine: a writable disk is `uw_add_disk`'s new write-through mode (`docs/plans/13-web.md`): the guest's writes and flushes go as synchronous POSTs to the loopback server, which writes them into the file through one `FileHandle` per disk and `synchronize()`s on a flush and when the run ends. Its NVRAM lived in memory for a run at first; it now persists ("NVRAM on both engines" below).
- Stopping the WebKit engine drains: the worker is asked to stop and the page is blanked only once it says it exited (or after 5 s). That matters because udisk map updates wait for a flush or the close (`docs/spec/uemulator-disk-format.md`); blanking at once killed the worker before the close and lost whatever the guest wrote since its last flush. A start during the drain waits for it.
- UI: a machine list (a split view; on a phone, a list that pushes the machine), New Machine (Alpine demo, a CD image or nothing; memory, a new disk, the display), Insert CD Image / Eject, the engine and display per machine, Delete (machine folder and disks; a CD image stays where it is). Launch arguments for scripted runs: `-machine NAME`, `-autostart`, `-new-machine NAME` with `-new-source demo|cdrom:FILE|empty`, `-new-disk-mib`, `-new-memory-mib`, `-new-display`. A first launch makes `alpine-demo`.
- The demo's initramfs now loads `virtio_blk`: without it a disk given to the demo never appeared, and `dd of=/dev/vda` quietly wrote a file in `/dev`, which is what the first tests here measured.
- Checked on the iPhone simulator, WebKit engine, a fresh demo machine with a 64 MiB disk: a 512-byte write with `conv=fsync`, then the app killed (`simctl terminate`), came back on the relaunched machine; a write followed only by `sync` (which flushes no device) came back after Stop and a relaunch, thanks to the drain. The udisk file grew by one cluster at the write, and the marker is in it. The native engine (interpreted on the simulator): the same `conv=fsync` write survived the app being killed.
- Not checked: NVRAM persistence end to end (the demo kernel exposes no EFI runtime: no efivarfs); an install of a real distribution (needs M5's network); the Mac app with these changes beyond a build (after a restart of this Mac, the app opened by `open -n` came up without a window until it was opened again).

## M3 as built (2026-11-15)

- Both engines draw into a `ScreenSurface` (`apple/App/ScreenSurface.swift`): a CoreGraphics bitmap in the library's XRGB8888, which is CoreGraphics' 32-bit little-endian skip-first layout, so rows are copied as they come. Each refresh copies only the changed rectangles and commits one `CGImage` (a copy-on-write copy of the bitmap) as the view's layer contents, aspect-fit, nearest-neighbour when magnified. A Metal texture fed only the rectangles is the upgrade if a phone shows the copy.
- Native: `ua_screen_update` keeps a `ScreenMirror` in the machine and hands Swift the screen and the rectangles whose pixels really differ (`DisplayHandle::sync_mirror`); `ua_cursor_update` hands the pointer image when its generation moves. Swift polls both at 60 Hz on the main run loop (cheap when nothing changed). Input is `ua_key` (USB HID usage), `ua_pointer_move` (screen pixels), `ua_pointer_button`, `ua_scroll`, `ua_release_all`, `ua_request_size`. Options are the web build's `DISPLAY`, `INPUT` and `SCREEN_CONSOLE` bits.
- WebKit: the bridge's binary messages got a kind byte. Page to app: console output, frames (the worker's `host_frame`: size, rectangles, packed pixels) and cursors; app to page: console keystrokes and input events, which the page writes into the worker's event ring as `main.js`'s `pushEvent` does. The app acknowledges every frame (`frame-ack` sets `FRAME_ACK`), so one frame is in flight and a slow bridge drops frames instead of queueing them.
- Keys: iOS sends `UIKey.keyCode`, which is the HID usage; the software keyboard (`UIKeyInput`) types characters, mapped to US-layout keys with shift. macOS maps `NSEvent.keyCode` (key positions, kVK_*) to HID usages in a table, and modifiers from `flagsChanged` with the device-dependent masks so left and right differ; caps lock is a press and release per toggle; repeats are dropped (the guest repeats).
- Pointer: absolute, through the inverse of the aspect fit. macOS: mouse, right and other buttons, wheel (trackpad points to notches); the guest's pointer image becomes the `NSCursor` (hidden or the host arrow otherwise). iOS: a touch is the pointer plus the left button, hover moves it (iPad trackpad), a two-finger pan scrolls; the guest's pointer image is drawn as a layer where the pointer is.
- Disks: `ua_config.disks` (path, read-only; raw or udisk, overlays refused with a message), and the WebKit engine serves them by byte range from the file (`FileHandle`, never the whole image) to `worker.js`'s synchronous range reads. The app boots an ISO with no kernel through the firmware: "Boot ISO…" in the machine menu, or `-cdrom NAME` (relative to the app's Documents) on the command line, with 2 GiB of RAM.
- The machine menu has the engine, the display (terminal only, screen, screen and terminal: the CLI's `--display serial|framebuffer|both`) and "Resize Guest to Fit"; the toolbar has a Terminal | Screen switch (in the bottom bar on iOS, where the navigation bar has no room).
- Checked: macOS, native JIT, Fedora KDE 44 live ISO: GRUB, the media check over the whole 3.1 GB image (PASS), Plymouth, the console in colour. iOS simulator, WebKit engine, Debian 13.7 netinst ISO: its themed GRUB menu, arrow keys from the hardware-key path moving the selection, `c` from the software keyboard opening GRUB's command line, and the GTK graphical installer: a tap on Continue moved X's pointer onto the button and advanced to the next page. On iOS the software keyboard is opt-in (a keyboard button in the bottom bar): the view keeps the focus for hardware keys with an empty `inputView`, since a touch is the pointer.
- The KDE desktop, at first not reached: after Plymouth the screen stayed black, the same in the CLI, with a Qt process crashing every 30 to 40 s. That was the emulator: `pcmp[ei]str[im]` raised #GP on a misaligned memory operand, which the SDM says they never do, so every Go program that searched a string of 16 bytes or more died, among them Fedora's podman quadlet generator, and DrKonqi crashed on each core dump (fixed in `cpu/sse_ext.rs`, merged into this branch; `docs/plans/24-display-input.md`). With the fix, the Mac app (native JIT, 4 GiB, the screen as console, the ISO's default GRUB entry with its media check) shows the Plasma desktop with its taskbar and the Welcome Center 12 minutes after the start.
- Not checked: the macOS pointer (nothing here can drive a Mac mouse), an iPad with a real keyboard and trackpad, and how a phone copes with 4 MB images at 60 Hz.

## M2 as built (2026-11-14)

- `apple/WebEngine/engine.{html,js}` is the page: main.js's job without the UI. It starts `worker.js` unchanged (no compile worker: that only helps V8), writes keystrokes, sizes and the stop flag into the shared control block as main.js does, and passes the worker's output and events on.
- The bridge is one WebSocket per run, page to app on 127.0.0.1 (`Loopback.swift`: an `NWListener` with `NWProtocolWebSocket`). The page's first message is `<token> <run>`; the app drops any socket that does not say the current run. App to page: a JSON `boot` (paths of the kernel, initrd and firmware, `uw_create`'s option bits, memory, size), then `resize` and `stop`; binary frames are keystrokes. Page to app: binary frames are console output (the worker's 16 ms / 64 KiB batches), text is `started`, `exit` (worker.js's codes) and `log`.
- The page, the web build and each run's kernel, initrd and firmware come from a minimal HTTP/1.1 server on 127.0.0.1 (same file), under a random per-launch token in the first path segment, with ranges (worker.js's disk reads) and the COOP/COEP/CORP headers. Disks are passed through to worker.js as URLs on it; the demo has none, so that path is only as tested as M0's range probe.
- `WebKitEngine` loads the page afresh for every start (with the run number) and blanks it on stop, which ends the worker. A cancelled load (stop then start in quick succession) is not a failure; a WebContent crash is reported as the machine stopping. The web view sits 1×1 at opacity 0 behind the terminal.
- `MachineEngine` is the protocol both engines implement; the toolbar has an engine menu (also `-engine native|webkit`, remembered in `UserDefaults`). WebKit is the default on iOS, native on macOS. The chip says `JIT`, `interp` or `wasm`.
- iOS simulator, Alpine demo through the UEFI firmware: the shell in about 9 to 11 s on WebKit against about 50 s on the native interpreter (the same ratio as M0's direct boots). Typing, Stop, Start again and the guest's own `poweroff -f` (reported as Powered off) work. The Mac app runs the WebKit engine too (sandboxed, with `com.apple.security.network.server` for the listeners).
- Not done: disks in the UI, persistence (M4), the screen (M3), a real device.

|---|---|---|

- **Verdict: build `WebKitEngine`.** It boots 6.5× faster than the native interpreter, which is all an App Store build gets otherwise, and within 1.4× of V8 without its compile worker. Against V8 with the worker it is 1.9×, so JSC's per-module cost is what is left to close (above).
- Isolation: no `SharedArrayBuffer` on a custom scheme even with `crossOriginIsolated` true; loopback HTTP has it, and shared wasm memory too. This moved the engine off `WKURLSchemeHandler`.
- Hidden: the web view ran both boots while 1×1 at opacity 0 in the hierarchy. Not tested yet: what happens when the app goes to the background (iOS suspends the app and its WebContent process; that hits `NativeEngine` the same way, and is the app's problem, not the engine's).
- Memory: a worker grew a wasm memory, touching every page, to 2560 MiB before `Out of memory`. On the simulator this is WebKit's own limit, not a device's jetsam limit.
- Still to do on a real iPhone and iPad (needs a signing team): the same table, the memory ceiling under jetsam, and the oldest iOS that has wasm tail calls. The simulator runs macOS's WebKit on the Mac's cores, so its absolute times flatter a phone; the ratios between rows are what carries over.

## Open questions

- Does App Review accept a hidden `WKWebView` used as a WebAssembly compute engine? Guideline 2.5.2 is about downloading executable code. The wasm here is bundled, and the generated modules are made from guest code at run time, which is what the JS engine is for. UTM SE's review history is the closest precedent and should be checked before M2.
- Multiple machines at once on `WebKitEngine`: one web view per machine (one WebContent process each, separate jetsam budgets), or one shared. One per machine is simpler and isolates crashes.
- Whether the library's validation of a machine config (what `main.js` checks before Start) should become a public `MachineConfig::check` or stay per-host.
