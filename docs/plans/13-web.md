# WebAssembly port

**Status:** implemented; "Not done" below lists what is missing.

`crates/uemulator-web` builds the library to `wasm32-unknown-unknown` (empty crate on any other target) and `crates/uemulator-web/www` is the page around it. `hack/web.sh [serve]` builds into `target/web` and serves it on `http://127.0.0.1:8080/`; `hack/web/serve.py` adds the two headers that make the page cross-origin isolated.

## What is ported

- Hot code runs on a WebAssembly JIT (below; the page has a checkbox, and `uw_create` takes the flag). Network: a virtio-net NIC on an Ethernet segment the page's tabs share ("The shared network" below); nothing leaves the browser unless the page has a Wisp server (`?wisp=`, "Internet through Wisp" below). Console: virtio-console (`hvc0`) or, by choice, the 16550 (`ttyS0`); the 16550 carries early boot text and the firmware's console either way.
- Firmware: the built-in UEFI firmware (the default, as in the CLI), a direct 64-bit kernel boot, the library's BIOS (boots the disk's boot sector), or a firmware image the user picks (a `UEMUFW64` image is booted as UEFI, anything else as a real-mode image ending at 1 MiB; OVMF is not supported). `hack/web.sh` builds `crates/uemulator-firmware` for `x86_64-unknown-none` into `target/firmware` and copies it next to the module as `uemulator-firmware.bin`; the page fetches it only when it boots through UEFI, so the module stays free of it. Under UEFI the kernel is optional: without one the firmware boots the disk (its `\EFI\BOOT\BOOTX64.EFI`). The firmware's variables live in a `MemoryKeyValueStore`: they survive a guest reset, not the page.
- Options on the page: memory, vCPUs (they take turns on the worker's thread), console kind, display (terminal only, a screen that is the console, or a screen beside the terminal as console) and keyboard and mouse (with or without a screen), the shared network (on by default; `?network=0` turns it off), JIT, ACPI, the AMD IOMMU (needs ACPI, and a guest kernel with `AMD_IOMMU`; Alpine's virt kernel has none), virtio-rng and whether a guest reset restarts the machine. The command line is appended to the library's default (`acpi=off` goes with ACPI on, `console=` follows the console kind), or replaces it.
- Up to eight drives (`vda`, `vdb`, ... in the page's order), each a raw or udisk image picked as a file or given as a URL, read on demand and never downloaded whole, and attached as a CD-ROM (read-only: the virtio-blk RO feature, no overlay) or a disk. `uw_add_disk(source, length, read_only)` (before `uw_create`, once per drive) wraps the page's source in a `RemoteImage` (256 KiB chunks, 64 MiB LRU, 2 MiB read-ahead on sequential misses) whose fetch is the import `host_disk_read(source, offset, ptr, len)`: the worker serves it with a synchronous `XMLHttpRequest` with a `Range` header (allowed in a worker, refused unless the answer is 206) or `FileReaderSync` on a `File` slice. A disk's writes go to an in-memory udisk overlay over it and are lost when the machine stops. An overlay image cannot be streamed (its base would need a second source); flatten it with `uemulator disk convert`. A CD is still a virtio disk to the guest (`vda`, not `sr0`): Linux finds an ISO's label on it the same way (`inst.stage2=hd:LABEL=`, `root=live:CDLABEL=`, Alpine's boot repository), and the UEFI firmware boots a hybrid ISO through its GPT or MBR and a plain one through its El Torito catalog (`docs/plans/19-uefi-firmware.md`). `WEB_DISK=IMAGE hack/web.sh` links an image as `assets/disk` and the page prefills it; `node hack/wasm/boot.mjs --disk FILE|URL --cdrom ISO` does the same under Node (both repeat).
- Boots the Alpine netboot kernel and initramfs to userspace in about 1 s of guest time and roughly 15 s wall clock in Chrome (about 20 s through UEFI); with the distro's init it ends at `Mounting boot media: failed` like the UEFI app, so the page defaults to `rdinit=/bin/sh`, which gives a working busybox shell (keyboard included). An installed Alpine disk (32 GiB raw, streamed from `hack/web/serve.py`) boots through the UEFI firmware and its GRUB 2.14 to the login prompt in about 2 minutes under Node, reading 98 MB of it.

## The page

A settings sidebar beside the console (an overlay below 900 px, toggled from the bar): presets (live CD or installer ISO: UEFI, 2 GiB, the screen as console; disk image; Linux kernel to a shell; the demo when there is one; the CD and disk presets drop any kernel and its command line, since under UEFI a kernel wins over every drive, and the kernel preset drops the demo's), the drive list (add a CD or disk from a file or URL, reorder, switch kind, remove; files dropped anywhere are attached, an ISO 9660 image as a CD, a bzImage as the kernel, the rest as disks), the kernel, initramfs and command line (shown only where they apply), firmware, hardware and an Advanced section. Notes above Start refuse what `EmulatedMachine::new` would (a direct boot without a kernel, UEFI or BIOS without anything to boot, more than one vCPU or the IOMMU without ACPI) before anything is downloaded, and warn about what boots but fails later: a CD with less than 2 GiB (Fedora's 252 MB installer initramfs fails to unpack in 1 GiB, `Initramfs unpacking failed: write error`, and the kernel panics with `VFS: Unable to mount root fs`, which Fedora's `drm_panic` draws on the screen), a kernel and drives together under UEFI (the drives are only attached), and a drive's boot loader with no screen (an ISO's GRUB passes no `console=` for hvc0 or ttyS0, so nothing shows after its menu). The library's own errors (a kernel without an EFI stub under UEFI) show in the status. While the machine runs the sidebar is locked; the bar shows the uptime and a summary, Terminal | Screen, resize-guest-to-fit, Ctrl+Alt+Delete (to the virtio keyboard, since the browser keeps the real one), a PNG screenshot, full screen and Stop; when it ends a banner gives the reason and Boot again. Settings other than picked files (URLs included, drives too) are remembered in `localStorage` (`uemulator.settings.v2`); `?args=`, `?firmware=`, `?console=`, `?display=`, `?memory=`, `?kernel=`, `?initrd=`, `?hypervisor=`, `?hypervisor-args=`, `?cdrom=` and `?disk=` (both repeat), `?iommu` and `?autoboot` set them from the URL. `node hack/wasm/boot.mjs` takes `--firmware`, `--cpus`, `--memory`, `--iommu` and `--no-acpi` for the same paths without a browser.

## The shared network

Every tab of the page (same origin, same browser profile) that runs a machine with the Network switch on puts its NIC on one Ethernet segment, 10.0.2.0/24: DHCP gives each guest its own address (10.0.2.15 and up), and the guests ping each other and talk TCP and UDP directly. 10.0.2.2 answers ARP, ping and DHCP and is the guests' router and DNS server: DHCP always says so, and a tab's own gateway terminates whatever is off the subnet ("Internet through Wisp" below). Without a Wisp server every such connection fails at once (RST, ICMP port unreachable). The bar shows the guest's address and how many other tabs' machines are on the segment; its tooltip has the NIC's MAC and whether this tab is the DHCP server. Measured in the desktop app's browser pane: about 11 ms round trips between two Alpine guests.

Split of the work. The protocol is in the library, `SegmentAgent` (`crates/uemulator/src/segment/`, no_std, unit-tested on a fake transport in `segment/tests.rs`): it switches frames, serves DHCP, ARP and ping for the server address, and announces this tab's leases. JavaScript only carries frames and holds the election (`www/segment.js`):

- Transport: BroadcastChannel, the one same-origin channel every tab can open without a broker. Each tab listens on `uemulator-segment` (everyone), `uemulator-segment/tab/N` (its own, N a random u32) and, while it serves, `uemulator-segment/server`. Every message is `{from: N, frames: [ArrayBuffer...]}`. The agent learns which tab every source MAC lives behind (by frame, not by NIC: a guest may bridge other MACs, a Xen domU's for one) and sends unicast to that tab's channel only, so other tabs never copy a stream they are not part of; broadcast, multicast and destinations it has not learned go to everyone, frames for the server's MAC to the server channel. A SharedWorker could have been the switch and the single DHCP authority at once, but every frame would take one more hop through it, and it is another context with a lifetime and a debugging surface of its own; the Web Lock gives the single authority without it.
- The worker cannot take messages while `uw_run` runs, so the page listens (`joinSegment`) and writes each frame, with the sending tab's number, into a third ring of the control `SharedArrayBuffer` (`NET_OFFSET`, 512 KiB; a full ring drops the frame as a NIC out of buffers would) and notifies `HEAD`; the worker's idle wait skips its sleep while the ring has frames. The poll hook (`NetLink::pump` in `src/lib.rs`) drains it through `host_net_recv`, takes the guest's frames from the `NetHandle`, runs the agent and posts what it produced with `host_net_send` and `host_net_flush` (one message per destination channel per poll), straight from the worker (`createSegmentSender`). A tab's own broadcasts come back to its page; the agent drops frames from its own tab number.
- Election: `navigator.locks.request("uemulator-segment-server")`, asked for when a machine with a network starts and held until it stops. The holder sets `NET_SERVING` in the control block, which the agent reads every poll (`host_net_serving`); the browser hands the lock to the next waiting tab when the holder's tab closes or crashes. The page terminates the worker before it lets go, so two agents never serve at once. Heartbeats alone would have needed a timeout and still allowed two servers for a while.
- One server identity: 10.0.2.2 at the locally administered MAC 52:55:0a:00:02:02, whoever holds the lock. A takeover changes nothing the guests can see: their ARP caches stay right and a renewal (unicast to the server identifier) reaches the new server.
- Leases survive the server: every agent announces, on EtherType 0x88B5 (IEEE local experimental; never delivered to a guest), the addresses of the stations behind it: what the DHCP replies it delivered gave them and what they send from (so an address configured by hand is protected too). Every agent keeps the whole table, so the next server already knows what is taken; on taking over it sends a census (everyone announces at once) and offers nothing until the answers are in (500 ms), and no agent offers before it has listened for 2.5 s. A client that comes back with an address the table does not know gets it if nobody else has it (INIT-REBOOT and renewals); one held by another live station is refused with a NAK. Announcements carry no times: each agent ages its table on its own clock, as `performance.now()` differs from tab to tab. Leases are an hour; a closed tab's addresses are reused only after that, or sooner when the pool is full and nothing has shown them in use. Announcements also count the peers (a tab silent for 4 s is gone and the stations behind it are flooded to again).
- Each tab's NIC gets a random locally administered unicast MAC (`randomMac`), new at every boot, so a duplicated tab never shares one; `uw_set_network(mac, len, tab)` before `uw_create` adds the NIC (`MachineConfig::net`) and refuses a MAC that is not locally administered unicast. No offloads are declared (`NetOffloads`): the frames go to other guests, which need real checksums and MTU-sized frames.

`node hack/wasm/segment.mjs` (after `WEB_DEMO=1 hack/web.sh`) boots the Alpine demo three times under Node on this transport (BroadcastChannel and Web Locks need Node 24.2 or later; Node 26 is what it was run on, each machine in a worker thread, `hack/wasm/segment_machine.mjs`) and checks the whole story: three different addresses, pings between every pair and to 10.0.2.2, a TCP line through busybox `nc` and 4 MiB of random bytes compared by MD5 (about 2 MB/s, wrapping the frame ring eight times), then the serving machine stops, the next one takes over, a fourth machine asks it at once and gets an address none of the others had (the new server knows the leases only from the announcements: with them turned off it hands out the stopped machine's), a guest that asks again keeps its address, and everyone reaches the newcomer. About 40 s.

## Internet through Wisp

Design and results are in `27-wisp.md`; this is the part that touches the page. Each tab's worker runs its own `Gateway` (`crates/uemulator/src/gateway/`, the engine the CLI's usernet also drives) beside its `SegmentAgent` in `NetLink::pump`: a guest frame to the server MAC whose destination is off the subnet, or 10.0.2.2 port 53, goes to the gateway and every other frame to the agent. The gateway's streams are carried by a Wisp v1 client (`crates/uemulator/src/wisp/`) over one WebSocket that the page owns (`www/wisp.js`), since the worker cannot receive messages during `uw_run`:

- Worker to page: `host_wisp_send` queues encoded Wisp packets and `host_wisp_flush` posts them (`createWispSender`); the page sends each as one binary message. `host_wisp_status` reports the client's state (and the last close reason) for the bar's pill tooltip.
- Page to worker: a fourth ring in the control block (`WISP_OFFSET`, 1 MiB, `WISP_HEAD`/`WISP_TAIL`) of records (payload length as u32, event as u8, payload) for the socket's connecting, each message (at most 256 KiB, else the page closes the socket) and loss; the poll hook drains it through `host_wisp_recv`, and the idle wait stays awake while it has records. Unlike the frame ring it never drops (Wisp streams have no retransmission): what does not fit waits in JavaScript until the worker drains.
- Setting it: the "Wisp server" field under the Network switch, `?wisp=URL` (ws and wss as given, a relative URL against the page; anything else shows as invalid in the pill's tooltip). The page reconnects with backoff, 1 s doubling to 30 s, reset by a completed Wisp handshake, and when the worker reports the client's 10 s handshake timeout the page closes the socket and reconnects after the usual backoff. `hack/web.sh serve` writes `wisp.json` so the field starts on `serve.py`'s `/wisp/` when it is empty; the GitHub Pages build writes none and the field starts empty.
- `uw_set_wisp(resolver, port)` before `uw_create` names the resolver 10.0.2.2:53 becomes (1.1.1.1 from the page).

`node hack/wasm/wisp.mjs` (after `WEB_DEMO=1 hack/web.sh`; Node 24.2 or later, as is `segment.mjs`) is the end-to-end check, and `segment.mjs` and it take `--wisp URL` (`boot.mjs` has no network).

## Screen and input

A machine with `OPTION_DISPLAY` and/or `OPTION_INPUT` (`docs/plans/24-display-input.md`; the page always sends its input choice, `OPTION_SCREEN_CONSOLE` adds `console=tty0` and the preview follows) gets a canvas next to the terminal and a Terminal | Screen switch in the bar; a screen that is the console opens on the Screen view.

- Frames: the poll hook (`ScreenLink::send_screen` in `src/lib.rs`) sends at most one update per 16 ms and only once the page has drawn the last (`FRAME_ACK` in the control block, cleared by the worker when it sends, set by the page once the frame is on the canvas), so a busy page gets fewer, larger updates, never a backlog. The hook keeps a `ScreenMirror` of what the page shows and `DisplayHandle::sync_mirror` returns only the 64-pixel tiles that differ from it; the first frame is the whole screen. `host_frame(screen_w, screen_h, rects, count, pixels, stride)` gets those rectangles (four `u32` each) and the mirror itself, in the library's blue, green, red, unused: nothing on the guest's thread converts pixels. The worker copies the rectangles' rows into one fresh, unshared buffer (WebGL refuses views on shared memory) and transfers it to the page. `on_update` is not used: it runs under the device lock.
- Drawing: a WebGL2 texture the size of the screen; each rectangle is a `texSubImage2D` of the bytes as they came (as RGBA), and the fragment shader reads its pixel with `texelFetch` and swaps red and blue. Measured in the browser pane for a whole 1280x800 frame: 0.45 to 0.7 ms against 1.7 to 2.2 ms for `putImageData` (which also wanted RGBA, converted in Rust on the guest's thread before). WebGL2 is tried on a spare canvas first (a canvas that once had a WebGL context can never have a 2D one); without it a 2D canvas takes the frames, the channels reordered in the page's JavaScript. A lost context is restored and asks for the whole screen again: the page acknowledges with `FRAME_READY.RESEND` (2), and the hook starts a new mirror. The screenshot draws once more in the same task as `toBlob` (the drawing buffer is cleared once composited).
- Pointer image: `host_cursor(kind, w, h, hot_x, hot_y, ptr, len)` when `DisplayHandle::cursor` changes (0 the host's, 1 hidden, 2 an RGBA image); the page makes it the canvas's CSS cursor.
- Input: a second ring in the control `SharedArrayBuffer`, after the keystroke ring at `EVENT_OFFSET`: 4096 records of three `Int32` (kind, a, b), `EVENT_HEAD`/`EVENT_TAIL` in the control block. Kinds: key by USB HID usage (from `KeyboardEvent.code`, the CLI viewer's table, with its US-layout fallback for an empty `code`), pointer move in screen pixels, button, wheel, release everything, request a size. `host_input_events(ptr, cap)` drains it in the poll hook; the page notifies `HEAD` after writing either ring, and the worker skips its idle wait while events are pending.
- The page: the canvas shrinks to fit the pane or grows by whole pixels (`image-rendering: pixelated`), and pointer positions are mapped back to screen pixels. Swapping views and losing the focus release every key and button. The terminal is refitted only while it is in front (xterm's fit measures 0 columns when hidden, and that size would reach the guest). "Resize guest to fit" sends the pane size, debounced. Without a screen the Screen view is a placeholder of the pointer area that still takes keys and the pointer.

## Library changes

`target_os = "uefi"` became `cfg(freestanding)`, set by `crates/uemulator/build.rs` for UEFI and for `wasm32` targets other than WASI (`wasm32-wasip1` is the hosted test target, below). Freestanding means `no_std`, no threads, no clock and no `std::fs`: the vCPU runs on the caller's thread inside `EmulatedMachine::wait` and the host is reached through `MachineConfig::poll`, exactly as in 12-uefi.md. `libm` is a dependency on the same targets. The RTC starts at `unix_time`, which the page passes from `Date.now()`; guest time follows `performance.now()` through `MachineConfig::host_clock` (`ClockMode::Realtime`): a virtual clock crawls at one nanosecond per interpreted instruction, far slower than the wall, then jumps over every idle wait. A halted guest waits in the poll hook's `host_idle` (1 ms), so a due timer fires at most that late.

## Shape of the port

- No wasm-bindgen: `uemulator-web` exports a small C ABI (`uw_alloc`, `uw_add_disk`, `uw_set_firmware`, `uw_set_hypervisor` and `uw_set_gpu` before `uw_create`, which takes the memory, vCPU count and a set of `OPTION_*` bits, then `uw_run`, `uw_error_*`; the numbers are mirrored in `www/protocol.js`) and imports `host_output`, `host_input`, `host_resize`, `host_should_stop`, `host_idle`, `host_log`, the screen's `host_input_events`, `host_frame_ready`, `host_frame` and `host_cursor` and the network's `host_net_recv`, `host_net_send`, `host_net_flush`, `host_net_serving` and `host_net_status` (above), the Wisp uplink's `host_wisp_recv`, `host_wisp_send`, `host_wisp_flush` and `host_wisp_status` (below; `uw_set_wisp` before `uw_create` sets the resolver), and the GPU's `host_gpu_send` and `host_gpu_receive` (`docs/plans/25-gpu-3d.md`) from the `host` module. Building needs only `rustup target add wasm32-unknown-unknown`.
- `uw_run` blocks until the guest exits, so it runs in a Web Worker (`www/worker.js`). A worker cannot receive messages during a synchronous call, so the page talks to it through a `SharedArrayBuffer` (layout in `www/protocol.js`): a byte ring for keystrokes, a record ring for the screen's input events, a stop flag, the terminal size and the frame acknowledgement; the segment's frame ring (`NET_OFFSET`, `NET_HEAD`/`NET_TAIL`) and the Wisp ring (`WISP_OFFSET`, `WISP_HEAD`/`WISP_TAIL`, 1 MiB, records of at most 256 KiB, below). That is why the page must be cross-origin isolated (COOP `same-origin`, COEP `require-corp`) and cannot be opened from `file://`.
- Where the server cannot send those headers (GitHub Pages), `www/isolate.js` registers `www/isolation_worker.js`, a service worker that adds them (and CORP `cross-origin`, for the CDN's xterm scripts) to every response except range requests, and reloads once it is in control. A page already isolated (`hack/web/serve.py`) never registers it.
- Demo mode: `WEB_DEMO=1 hack/web.sh` runs `hack/web/demo.py`, which downloads Alpine's `vmlinuz-virt` and minirootfs (release and SHA-256 pinned in the script, cached in `target/web-demo-cache`), turns the minirootfs into a gzipped newc initramfs with an `/init` that mounts the pseudo file systems, loads virtio-net and packet sockets (the virt kernel builds them as modules; `failover`, `net_failover`, `virtio_net` and `af_packet` are taken from the release's netboot initramfs, also pinned) and runs `udhcpc` on eth0 when there is one, then starts a shell on the console's tty (so it has job control), pulls `boot/xen.gz` out of Edera's Xen image (`ghcr.io/edera-dev/xen`, its linux/amd64 manifest pinned by digest in `hack/web/demo-xen.ref`; the anonymous pull token, every manifest and layer checked against its digest, layers read in memory), and writes them with `demo.json` into `demo/`, 18 MB in all. `demo.json` lists machines: "Alpine Linux" (the kernel and initramfs: UEFI, serial console, 256 MiB) and "Edera Xen" (`xen.gz` booting the same pair as its dom0: 512 MiB with `dom0_mem=384M,max:384M`, since Xen's automatic dom0 share of 256 MiB is too small for the initramfs; the AMD IOMMU on and `dom0=pvh-auto`, so dom0 is PVH, or PV if the IOMMU switch is turned off). The welcome pane has a button per machine and the presets offer each; booting one loads it into the sidebar first, so what runs is what the settings show. `?autoboot` boots the first, `?autoboot&demo=xen` the Xen one. Alpine: a shell in about 20 s in Chrome, 12 s under Node; Xen: about 30 s in the desktop app's browser pane (Chromium), 19 s under Node (26 s as a PV dom0).
- Hypervisor: the kernel panel takes a hypervisor under UEFI (a file or URL; `xen.gz` or `xen.efi` dropped on the page becomes it; `xen.efi` only works as Edera builds it, see 18) and its arguments (empty: the library's `console=com1 com1=115200,8n1`). The kernel is then dom0, the console is forced to serial (Xen owns the 16550), the command line preview follows the library's dom0 default, and Start is refused without a kernel or under another firmware. `uw_set_hypervisor(image, len, cmdline, cmdline_len)` hands it over before `uw_create` (`docs/plans/18-xen-dom0.md`). Every preset other than the Xen demo clears it.
- `.github/workflows/pages.yml` runs `WEB_DEMO=1 hack/web.sh` on every push to main and deploys `target/web` as `web/` of the repository's Pages site (`https://edera-dev.github.io/uemulator/web/`), leaving the root for a real site. The build is never committed. The repository's Pages source must be "GitHub Actions". The published page has the demo but no `assets/`: other kernels and disks are picked or given as URLs, which under COEP must be same-origin or send CORS headers.
- Guest output is batched in the worker and posted every 16 ms. An idle guest sleeps in `Atomics.wait` on the ring head, woken by the next keystroke.
- wasm32 has 32-bit `usize`. The page offers 256 MiB to 3 GiB. Guest RAM is one flat buffer whose byte N is guest physical address N, and the PCI hole starts at 3 GiB, so more RAM would continue at 4 GiB, past the end of the 4 GiB a wasm32 memory can grow to; going further needs memory64. Rust allows no allocation, slice or `pointer::add` past `isize::MAX` (2 GiB here), so RAM larger than that is grown straight onto the module's memory with `memory.grow` (`ram::GuestRam::zeroed`), never freed (the page runs one machine per instance, and a guest reboot zeroes and reuses it), and nothing views all of RAM as one slice: `GuestRam` and the borrowed `RamSpan` (boot loaders, device DMA) hand out checked ranges, and `ram[start..]` stops at the longest slice there can be. The CPU and the JIT form host addresses as integers (`ram_base + physical`), which a wasm32 address holds up to 4 GiB. The module's memory then passes 2 GiB, and every pointer it hands JavaScript (`uw_alloc`'s result, the `ptr` of the imports) arrives as a negative `i32`: the worker, `jit_host.js` and `boot.mjs` read them as `ptr >>> 0`. A kernel and initramfs the page uploads sit in module memory beside the RAM (Fedora's netinst: 18 + 252 MB); with a 3 GiB guest that leaves about 1 GiB for them, the heap and the TLBs. Saved settings and links with the old 2047 MiB maximum become 2 GiB.

## The JIT

`jit/wasm.rs` (code cache and `Cpu::step_block`), `jit/emit_wasm.rs` (block generator) and `jit/wasm_encode.rs` (binary encoder) are the third backend; `docs/plans/06-jit.md` has the shared design. What is different here:

- A block is a WebAssembly module of its own with one export, `block: (cpu: i32) -> i64`, which imports the emulator's `memory` and function `table`. It reads and writes the `Cpu` and guest RAM directly (both live in the module's linear memory) and calls the helpers with `call_indirect`: a Rust function pointer on wasm32 is its table index, so `Addrs` is just those numbers. The helper types are fixed in `wasm_encode` (`FUNCTION_TYPES`); a wrong one traps and takes the emulator down.
- The library cannot instantiate a module itself. A module holds one or more block functions, exported as "0", "1", ... (`wasm_encode::module_of_functions`); the library hands its bytes to the host import `host_jit_compile(ptr, len, slots, count)` (`www/jit_host.js`: `new WebAssembly.Module` + `Instance` with `{env: {memory, table}}`, then a `table.set` per function, whose slot numbers it writes to `slots`), calls a block through its slot like a function pointer, and returns the slot with `host_jit_release`. The final link needs `--export-table --growable-table` (`uemulator-web/build.rs`, `.cargo/config.toml`).
- A compile worker (V8 only: Chrome, Edge, Node) takes the compiling off the emulator's thread. The page starts `www/jit_compiler.js` beside `worker.js` (a worker started by `worker.js` itself never runs in Chrome, as that thread is in `uw_run` from the start) and both share a compile queue, a `SharedArrayBuffer` ring of module bytes. A hot block's function is generated and queued (`State::pending`); the queued blocks go out as one module (`host_jit_submit`, up to `MAX_BATCH_BLOCKS` = 64) whenever the worker has none of ours (`MAX_IN_FLIGHT` = 1), so they batch up while it is busy. The worker compiles the module and calls each function once with a `cpu` pointer past the end of a one-page dummy memory (V8 compiles lazily, on the first call; the call traps at the first access) and keeps it alive. The emulator's thread keeps interpreting the block until `host_jit_ready` says the worker is done, then `host_jit_compile` makes a module of the same bytes, which V8 serves from its process-wide native module cache with the compiled code. A pending block's other instructions do not count heat (or every instruction of it would get hot and a block of its own while it waits), but every one of its instructions the interpreter runs looks for finished modules, and once it has run `PATIENCE` (8) passes' worth (8 times its instruction count, so a loop inside it counts too) the block is installed without waiting (its module is made here; V8 compiles only what runs, or finishes the worker's compile first). Without that, a loop inside a pending block (`mov ecx, N; l: ...; jnz l`, the loop body inside the setup block) ran interpreted to its end. A write to a pending block's page drops it (`invalidate_page`), and so does a flush; its function is thrown away when the module comes back. Straddlers are compiled at once. Once a worker takes modules the threshold drops from 40 to `COMPILE_THRESHOLD_WITH_WORKER` (10). Without a worker (other engines, `boot.mjs --no-compile-worker`, the WASI test runner) `host_jit_submit` refuses and every block is compiled at once in a module of its own, as before.
- No host flags: every flag writer leaves its operands and result in locals, and `cmp; jcc`, `setcc` and `cmov` are computed from them (`Fused`) with no call. The lazy record of an add, sub, logic op, cmp, test, inc, dec or neg (into a register) stays pending in those locals (`Gen::pending_record`) and is stored only where something can read it: before a helper call, on a slow-path access (the helper may fault, and the exception frame takes the flags from the record), at every exit, and before any instruction not known to leave the record's locals alone (`keeps_pending_record`); the next such flag writer just drops it. A flag writer into memory stores the old record first: it computes into the locals before its store, and a faulting store must leave the flags from before it. `helper_cond` covers what the locals cannot (after inc/dec the CF-reading conditions).
- Blocks run on past a conditional branch (`blocks::decode_block` with `past_branches`, the WebAssembly backend only): decoding continues with the instruction after a jcc while it is in the same page and the block has room (48 instructions), the taken branch becoming a side exit, so a block ends only at an unconditional transfer or an instruction that must end it. A block boundary is the expensive thing here (an indirect tail call into another module instance, after the checks of a linked exit), and blocks that ended at every jcc averaged 4.5 instructions in the KDE live ISO's boot against 10.3 after (16 instructions per block entry). Code a block runs on into is translated again where something jumps into the middle of it; the cache's size absorbs that. A block whose jcc or jmp targets its own first instruction is a wasm `loop` (`Gen::back_edge`): the back edge pays `icount` and checks the budget and `block_exit_requested` like a linked exit to itself, then branches back instead of tail-calling.
- Blocks chain: an exit is a `return_call_indirect` (a WebAssembly tail call) into the chain stub, one module compiled in `Jit::new` that does what `arch_x64::chain_stub` does (event budget, `block_exit_requested`, exec TLB, jump cache, validity) and tail-calls the successor or returns to the run loop. Without tail calls the stub fails to compile and the JIT runs unchained. The stub also enters straddling blocks once it has checked the second page's exec TLB entry, as `Jit::lookup_straddler` does (a hot loop crossing a page went back to the run loop on every pass: 2.7M returns in an Alpine boot).
- Link cells stand in for direct links (there is no code to patch): an exit to a fixed address in the block's own page reads the successor's block index and table slot from an 8-byte cell the block owns, checks the budget, `block_exit_requested` and the successor's validity byte, and tail-calls it; an empty or stale cell (index `NO_BLOCK`, never valid) takes a second stub, `LINK_TYPE` `(cpu, cell)`, which fills the cell on a hit. Straddlers are never linked. 80% of the 290M transitions of an Alpine boot are such exits.
- Compiling is the expensive part (about 38 us a block on the thread that does it), so a block is compiled only after its first instruction has run `COMPILE_THRESHOLD` times in the interpreter; until then `step_block` interprets one instruction. A tiering counter table (`Heat`) is indexed by physical address. Tests build with a threshold of zero.
- The function table belongs to one instance, so a second wasm thread could not call the blocks: with the JIT the vCPUs take turns on one thread even when a `thread_spawner` is given (`runs_on_threads`), and the jump cache is one table shared by all handles.
- A full cache (`MAX_BLOCKS` = 2^17; every block is a live function in the engine, about 10 KB of V8's memory each) makes room without throwing away the hot code (`State::make_room`): first the blocks invalidated since (their pages were written) give back their slot and their index (`State::reclaim`, after clearing the jump cache, whose entries would otherwise pass their validity check with a reused index); when too few are dead, every page none of whose blocks is in the jump cache or among the last quarter of translations is evicted as a guest write would (`State::evict_cold_pages`), and only a cache that is still hot after that is flushed. Link cells stay safe because a cell only names a block of its own page, and eviction, like a write, takes a page whole. At 2^16 blocks and with flushing only, the KDE live ISO's boot flushed six times in its first 145 s and spent the time recompiling the same code.
- adc/sbb are inline at 32 and 64 bits (the carry-in from the fused locals or `helper_cond`, the record `Adc`/`Sbb` with `lazy_src2`). 64-bit `imul` (two and three operand) and one-operand `mul`/`imul` take the high half of the product from 32-bit limbs (`Gen::mul_high`); a 64-bit `imul` whose flags the next flag writer overwrites skips it (`helpers::flags_dead_after`). rol/ror merge CF/OF through `helper_set_rotate_flags` unless dead. Also inline, following the aarch64 backend: shl/shr/sar of 8- and 16-bit operands, shlx/shrx/sarx, bzhi, andn, blsr/blsmsk/blsi, bsf/bsr/tzcnt/lzcnt, shld/shrd by an immediate, bswap and movzx from ah..bh; and mulx, whose operands stay out of the fused locals (it changes no flag).
- Vector instructions: the whole-register moves (legacy movups/movaps/movdqu/movdqa and the unmasked EVEX vmovdqu*/vmovdqa*/vmovup*/vmovap* at 16, 32 and 64 bytes) and kmovd/kmovq between opmask and general registers need nothing but i64 loads and stores; with fixed-width SIMD (`probe_simd` at `Jit::new`, `Addrs::simd`) also the legacy `66 0f` integer instructions (pxor, pcmpeq*, pminub, padd*, pmovmskb, ...), movd/movq between xmm and general registers or memory, the unmasked EVEX integer logic and arithmetic, and the AVX-512 byte compares and tests into an opmask (vpcmpeqb, vpcmpub/vpcmpb, vptestmb/vptestnmb, each 128-bit lane through i8x16.bitmask): glibc's EVEX string and copy loops. Each checks the `Cpu::sse`/`Cpu::evex_gate` conditions once per block, an aligned form's alignment and a TLB hit for the whole operand, and otherwise runs the instruction in the interpreter from inside the branch (`Gen::helper_in_branch`, which prepays the clock only for the call). A masked store, broadcast and the rest stay in the interpreter.
- A cold step whose heat entry is its own and still below the threshold skips the block map search (`Jit::known_cold`).

## Tests

The library's suite runs on `wasm32-wasip1` under Node, so the JIT is exercised by the same differential corpus as the native backends (`jit/diff_*.rs`, `assert_jit_matches_interpreter`):

    cargo test --release --target wasm32-wasip1 -p uemulator --lib -- --test-threads=1 jit::

`.cargo/config.toml` points the runner at `hack/wasm/test-runner.sh` (`run-wasi.mjs`: Node's WASI plus the same `host_jit_*` imports as the page; wasmtime cannot compile new modules for its guest). WASI has `std` but no threads, so `wasm32-wasip1` is built hosted (not `freestanding`), and what needs a second thread (`EmulatedMachine::start`, the `smp`/`atomic` threaded tests, `netdev` wake-ups) or an unwinding panic cannot run there; a panicking test aborts the process (wasm has no unwinding), so run a module at a time to find the failing test. `diff_tests.rs` and `wasm.rs` pin that the JIT is really in use (the corpus skips itself without one). The pure encoder tests also run on the host.

`node hack/wasm/boot.mjs --kernel K --initrd I [--no-jit] [--debug] [--until TEXT]` boots a kernel on the real `uemulator_web.wasm` (the page's module and imports) under Node and prints the time to a console message: a Debian netboot kernel reaches `Machine keyring initialized` in about 6 s with the JIT against about 55 s interpreted, and goes on to start the installer.

## Not done

- Keeping the disk's writes across page loads (a udisk overlay in OPFS instead of memory), and the raw Ethernet relay and `fetch()` models of internet access (`27-wisp.md`, non-goals).
- Masked EVEX moves (glibc's tails), vpbroadcastb from a general register, adcx/adox (bignum code: host key generation; each changes one flag, which the lazy record cannot say without materializing the rest), and a JIT per worker for SMP.
- The compile worker on Firefox and Safari: no measurement says whether their engines share compiled code between threads, so the page does not start it there (`compileWorkerHelps`), and those engines compile on the emulator's thread one block per module as before. More than one compile worker, and smaller block code (18 us of Liftoff per KB), would shorten the wait for a module further.

## Performance (2026-10-31, Alpine 6.18 virt kernel and initramfs, Node 26, Apple Silicon)

`node hack/wasm/boot.mjs --firmware none --kernel vmlinuz-virt --initrd initramfs-virt --until "Run /init"`, best of four interleaved runs on a loaded host: 12.2 s before, 9.7 s with link cells (10.2), the straddler path and adc/sbb (10.0) and the cold-step shortcut (9.7); dead-flag imul/rotates moved helper calls from 6.1M to 5.4M but not the wall time measurably. Guest timestamps follow the wall clock, so they show the same phases; the SMP alternatives phase is not self-modifying-code bound (1.3k page invalidations and 13k invalidated blocks in the whole boot, no stale decodes). `--debug` prints the counters this is based on.

Where the time goes now (CPU profile): about half in generated code, about 1.8 s compiling blocks (module creation plus lazy Liftoff compilation on the first call, which V8 most likely attributes to `step_block`: its self time is 15-19% of the profile), the rest in the run loop and the interpreter for the 5.9M cold steps and 5.4M helper calls. `--wasm-tiering-budget=1000000` (Node only; a page cannot set it) is 10% faster, so hot blocks spend a while in Liftoff code before TurboFan takes over. What would pay next: several blocks per module (synthetic benchmark: about 15 µs fixed per module against about 2 µs per function when 32 share one), smaller blocks (the slow path of every memory access is inline, and link cells made module compilation about 15% slower, which is why the code-heavy SMP alternatives phase did not get faster), and 64-bit `imul` flags without the interpreter.

What a block costs the vCPU thread (2026-11-01, the demo's Alpine kernel and initramfs to `Run /init`, Node 26, about 6.4 s and 33k modules of 600 bytes on average, host load 6 to 10): about 38 us, 1.25 s of the boot. `host_jit_compile` timed step by step: copying the bytes out 1.4 us, `new WebAssembly.Module` 18.2, `new WebAssembly.Instance` 4.5, `table.set` 0.6. The rest is not in `boot.mjs`'s `compile=`: V8 compiles a function lazily (Liftoff) on its first call, about 13 us, measured three ways that agree: `--no-wasm-lazy-compilation` doubles the `Module` time (18 to 36 us) and leaves the boot time unchanged; a block's first call minus its second, both trapping at once on a `cpu` pointer past the end of memory, is 11 to 14 us; and that difference fits 4.4 us plus 18 us per KB of block code (45 us for blocks over 1.6 KB). Offline, on the dumped modules with their bodies merged unchanged into one module (they never call by function index), `Module` plus `Instance` per block is 15.5 us alone, 7.0 at 4 per module, 3.0 at 16 and 1.1 at 64; the first-call compile stays about 13 us at every size, so batching alone gets a block to about 16 us. The offline single-module cost is lower than in the boot (15.5 against 22.7 us), not explained; it may grow with the number of live instances.

A module compiled in a worker carries its code: a worker built the modules, instantiated them against a dummy memory and table and called every export once (trapping) to compile it, then posted the `WebAssembly.Module`s; on the receiving thread the first call cost no more than the second, at 1, 16 and 64 blocks per module. So compiling off the vCPU thread leaves it only the instance and `table.set`, about 5 us a block unbatched and 2 to 3 batched, which beats batching alone. It needs the vCPU worker to take messages while the machine runs (JSPI, or a `uw_run` that returns to the event loop in slices) and keeps a block interpreted until its module arrives, a cost not measured. Firefox and Safari were not tried. Batching still cuts instances and messages, but a page's module must not be rebuilt as more of its blocks get hot: new bytes are a new module, and every block in it pays the first-call compile again. Batch the blocks waiting to be compiled across pages (each keeps its own validity) or build a page's module once and put later blocks in another. How many hot blocks a page has, which decides what batching saves, was not measured.

What was built (above, "The JIT"): no messages are needed after all. V8's native module cache is keyed by the module's bytes, so a worker that compiled the same bytes is enough: in Node, `new WebAssembly.Module` of them on another thread cost 3.4 us and left nothing to compile on the first call (0.4 us a block at 16 per module); in Chrome 152 (the desktop app's browser pane) 11 us and nothing on the first call, and in a noisier run with the pane hidden about 3 us a block at 64 per module against 4.5 uncached, plus the 12 to 13 us first-call compile the uncached ones still had to pay. A compile worker started by the emulator's worker never ran in Chrome; one started by the page did. `--wasm-native-module-cache` is on by default in V8; other engines are assumed to have no such cache (`compileWorkerHelps`).

Results (Alpine demo kernel and initramfs to `Run /init`, Node 26, interleaved, host load 6 to 11): HEAD 5.28 to 5.48 s, this change without the worker 5.36 to 5.54, with it 3.66 to 3.87 (35k blocks in about 7.8k modules, the emulator's thread spending 240 ms in `host_jit_compile`, 2.3M cold steps against 5.5M). The Xen PVH demo (`hack/perf/xen.sh pvh-iommu wasm`): 11.5 s before, 8.4 after. In the desktop app's browser pane (hidden, so throttled alike) the Alpine demo reached its shell prompt 5.6 s after the page loaded, twice, against 8.1 s for HEAD (a second HEAD run took 39.5 s and is left out as an outlier). How it got there, each step measured on the Alpine boot: the worker with one block per module and no patience gave nothing (5.4 s: every block waited a median 1.3 ms, p99 9 ms, for the worker, which fell behind in bursts, and was interpreted meanwhile, 7.5M cold steps against 5.5M); patience made it 5.1; batching 64 blocks into one module in flight 4.0 (8 per module and 8 in flight 4.5, 16 and 4 4.2, 64 and 2 4.1; 128 and 256 per module the same as 64; patience 4 to 32 within noise); the threshold of 10 3.7 (3 and 5: 4.0 and 3.9; 20: 3.8). Turning off stack traces for the worker's traps changed nothing measurable but is kept (`Error.stackTraceLimit = 0`). About 5k of the 35k generated blocks are thrown away because their page was written while they were pending; without the worker the same blocks would have been compiled and then invalidated. Looking for modules from inside pending blocks too (above) came after these steps and kept the time at 3.7 s.

The page's half can only cost speed, never correctness: the emulator's thread always makes its modules from its own bytes, and the worker's compiled code is used only when V8's cache finds those exact bytes, so a bug in the queue or the tickets shows as `boot.mjs` reporting more `compile=` time per module (about 30 us instead of 3), not as wrong guest behavior. The library's tests drive the pending path with a fake compiler (`jit::wasm` tests); the WASI test runner has no worker, so the queue itself is exercised only by `boot.mjs`, `segment.mjs` and the page.

Guest registers in locals (tried, not kept): each register a block touches loaded into a local on first use and written back before every exit and every helper call. It made no measurable difference: an interleaved best of five through UEFI (`--firmware uefi`, same command otherwise) was 7.21 s before and 7.41 s after on a host whose single runs spread from 7.2 to 11.5 s, and a self-linked 8-instruction loop of 240M guest instructions under the WASI runner took 156-160 ms against 158-164 ms. It also made modules about 10% larger (596 to 659 bytes on average), because every exit and every slow path repeats the write-back. The loads it saves are L1 hits next to what a block pays to start and to leave (about 5 ns per iteration of that loop, most of it presumably the exit sequence: `icount`, budget, `block_exit_requested`, the link cell and the valid byte, then a tail call into another instance). Locals would only pay where they cut that cost, for example a self-loop compiled as a wasm `loop` that loads its registers once and writes them back when it leaves. `jit/diff_registers.rs` keeps the cases such a change has to pass, and notes the one hazard they cannot cover: the slow-path load/store helpers can take an SVM #VMEXIT, which rewrites rsp and rax in `Cpu`.
