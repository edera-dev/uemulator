# TPM 2.0 and Secure Boot

**Status:** implemented: the TPM device (measured boot, then keys, HMAC and policy sessions, NV indices, contexts and persistence in the machine's key-value store), the firmware's TCG2 protocol and event log, Secure Boot with Microsoft's keys, authenticated variable writes, `--tpm`/`--secure-boot` on the CLI and the web page. Not implemented: signing, attestation and an EK certificate (below, "Next").

Both are off by default and independent: `MachineConfig::tpm(true)` adds the TPM, `MachineConfig::secure_boot(true)` makes the UEFI firmware enforce Secure Boot. A Windows-11-style machine turns on both.

## Crates

`crates/uemulator-crypto` (`no_std` + `alloc`, no dependencies) has what both need: SHA-1/256/384/512, RSA PKCS#1 v1.5 verification (Montgomery, up to 8192 bits), a DER reader, X.509, PKCS#7 `SignedData` (wrapped or bare, embedded or detached content, chains to an anchor that may be an intermediate, no time or key-usage checks, as EDK2) and the Authenticode PE digest. For the TPM's keys and sessions it also has HMAC, KDFa/KDFe, AES with the TPM's CFB mode, RSA private keys (deterministic generation from a random stream, rebuilding from one prime, CRT, OAEP both ways, PKCS#1 v1.5 signing; general big-number arithmetic in a private `bignum`) and P-256 (ECDH, ECDSA). None of it is constant time, so the TPM's secrets are only as safe as the emulator process. On x86_64 SHA-256 uses the SHA extensions when CPUID has them, in inline assembly that saves the XMM registers it uses (the firmware's target is soft-float, where LLVM cannot lower vector types, and the firmware is called through the Microsoft ABI). The library depends on it for the TPM's hashes, which makes it the library's one dependency without `jit`; it is first-party, so "no third-party dependencies" still holds.

## The TPM device (`crates/uemulator/src/dev/tpm/`)

- Interface: CRB (TCG PC Client Platform TPM Profile) at 0xFED40000, one page: locality 0 registers, the control area at +0x40, the data buffer at +0x80 (3968 bytes, which bounds commands and responses). QEMU's `hw/tpm/tpm_crb.c` is the reference. A command runs synchronously in the write that sets `CTRL_START`, so `START` reads back clear at the first poll and no interrupt exists. Only locality 0.
- ACPI: the `TPM2` table (revision 4, start method 7, ending after the start-method parameters: no LAML/LASA, since Linux takes the log from the UEFI configuration table and warns about an empty log area) and `\_SB.TPM` with `_HID "MSFT0101"` and the page in `_CRS`. Linux's `tpm_crb` binds to it. Linux also prints "Disabling hwrng": it takes an `MSFT0101` CRB on an AMD CPU for AMD's fTPM, whose RNG it distrusts. Harmless (virtio-rng feeds the pool).
- Commands (TPM 2.0 Library 1.59), `engine.rs` dispatching, `TPM_CAP_COMMANDS` listing exactly these:
  - Start-up and the rest of measured boot: Startup (CLEAR only: there is never saved state), Shutdown, SelfTest, IncrementalSelfTest, GetTestResult, GetCapability (algorithms, handles of every type, commands, PCRs, TPM properties, PCR properties, ECC curves (P-256), empty lists for the rest), TestParms, GetRandom (the machine's entropy, seeded under `--verify`), StirRandom, PCR_Read, PCR_Extend, PCR_Event, PCR_Reset (16 and 23), Hash, HashSequenceStart, SequenceUpdate, SequenceComplete, EventSequenceComplete, ReadClock.
  - Objects (`object.rs`): CreatePrimary, Create, Load, ReadPublic, Unseal, EvictControl, ECDH_KeyGen, ECDH_ZGen. What can be made: RSA 2048 (exponent 65537) and ECC P-256 storage parents (restricted decrypt, AES-128/256-CFB) and unrestricted decrypt keys (RSAES/OAEP, ECDH), and sealed data (`KEYEDHASH` without sign or decrypt, up to 128 bytes). Signing keys, HMAC keys, symmetric objects and derivation parents are refused (`TPM_RC_ATTRIBUTES`, `_TYPE`): nothing could use them. A primary is derived from the hierarchy's seed by a KDFa stream over the template's name and the sensitive data, so the same template gives the same key (not bit-for-bit the reference implementation's derivation; seeds never leave a TPM, so nothing can tell). A child's private area is the spec's protected form: `outerHMAC || AES-CFB(TPM2B_SENSITIVE)`, keys from the parent's seed by KDFa("STORAGE"/"INTEGRITY") and the child's name; Load checks the HMAC, then that the secret belongs to the public area. Creation data and creation tickets are real (HMAC with the hierarchy's proof).
  - Sessions (`session.rs`): password, HMAC and policy (and trial) sessions, bound or not, unsalted or salted by RSA-OAEP ("SECRET") or ECDH plus KDFe; command and response HMACs as Part 1 has them (cpHash over the parameters as sent, response HMAC with the entity's value after the command, so the new one after HierarchyChangeAuth); AES-CFB parameter encryption of the first command or response `TPM2B` (decrypt and encrypt allowed per command, `CommandSpec`); a session that only encrypts has its command HMAC ignored. Policy: PolicyPCR, PolicyAuthValue, PolicyPassword, PolicyGetDigest, PolicyRestart; a policy session resets after it authorizes, and a PCR change after PolicyPCR is `TPM_RC_PCR_CHANGED`. No audit sessions, no XOR obfuscation. Up to 8 loaded and 64 active sessions.
  - NV (`nv.rs`): NV_DefineSpace, NV_UndefineSpace, NV_ReadPublic, NV_Read, NV_Write, ordinary indices up to 2048 bytes (64 indices, 64 KiB), owner or platform, authorized by the index's value or policy, the owner or the platform as its attributes allow. Counter, bit, extend and PIN indices are refused; lock attributes are accepted and never act (no lock commands).
  - Contexts (`context.rs`): ContextSave, ContextLoad, FlushContext. Linux's resource manager saves and reloads every object and session around each command through these. An object's context is the whole object, encrypted and HMACed with a secret made at each TPM Reset (and the hierarchy's proof, so `TPM2_Clear` invalidates them); a session's state stays inside the TPM in a saved state and only its latest context loads. Hash sequences cannot be saved.
  - Hierarchies (`hierarchy.rs`): Clear (new storage seed and proofs; the owner's and endorsement objects, persistent ones, and the owner's NV indices go; authorizations empty), HierarchyChangeAuth, DictionaryAttackLockReset (there is no lockout).
- Anything else is `TPM_RC_COMMAND_CODE`. `TPMA_CC` handle counts are what Linux's resource manager relies on. A transient object or session that is not loaded is `TPM_RC_REFERENCE_H0` plus the handle's position (Linux reads that as flushed); other missing handles are `TPM_RC_HANDLE`.
- One PCR bank, SHA-256 (swtpm's default too). PCRs 17 to 22 start as all ones and need a locality above 0, so they can be read but not changed. Hashing (`TPM2_Hash`, sequences, `PCR_Event`) takes all four SHA algorithms.
- Persistence: the platform, endorsement and storage seeds and proofs, the owner, endorsement and lockout authorizations (`tpm/state`), persistent objects (`tpm/persistent/<handle>`, up to 16) and NV indices (`tpm/nv/<index>`) live in `MachineConfig::key_value_store`, a named machine's `nvram.kv`; without one the machine makes an in-memory store that lasts as long as it. They are stored in the clear, as swtpm's state file is. The guest's own port onto the store (`dev/kv.rs`) cannot see, write or delete `tpm/` keys. The `--verify` twin gets a copy. The null hierarchy's seed, the platform authorization and the context secret are new at every TPM Reset.
- Nothing is constant time (`uemulator-crypto`), so a guest able to time the emulator precisely could in principle learn secrets; the TPM is a convenience for measured boot and disk unlocking, not a security boundary against the guest itself.
- Volatile state (PCRs, loaded objects, sessions) lasts as long as the `Devices`: a guest reset builds new devices, which is `_TPM_Init`.

## Measured boot (`crates/uemulator-firmware/src/tpm.rs`, `tcg.rs`)

The firmware starts the TPM (`TPM2_Startup(CLEAR)`; `TPM_RC_INITIALIZE` is accepted), reads the allocated banks, keeps a crypto-agile log (64 KiB of boot services data, `Spec ID Event03` first) and a final events table (16 KiB of ACPI NVS, installed as `EFI_TCG2_FINAL_EVENTS_TABLE_GUID`), and publishes `EFI_TCG2_PROTOCOL` (GetCapability, GetEventLog for the TCG 2 format, HashLogExtendEvent with `EXTEND_ONLY` and `PE_COFF_IMAGE`, SubmitCommand, GetActivePcrBanks; SetActivePcrBanks only accepts the current allocation). After `GetEventLog` events also go to the final events table. What it measures (PC Client PFP 1.05):

| PCR | event | when |
|---|---|---|
| 0 | `EV_S_CRTM_VERSION` "uemulator UEFI firmware 1" (UTF-16) | TPM start-up |
| 7 | `EV_EFI_VARIABLE_DRIVER_CONFIG` SecureBoot, PK, KEK, db, dbx (empty ones too), then `EV_SEPARATOR` | start-up |
| 1 | `EV_EFI_VARIABLE_BOOT2` BootOrder and each Boot#### it lists | first boot attempt |
| 4 | `EV_EFI_ACTION` "Calling EFI Application from Boot Option" | each attempt; "Returning ..." after |
| 0-6 | `EV_SEPARATOR` | first boot attempt |
| 4 / 2 | `EV_EFI_BOOT_SERVICES_APPLICATION` / `_DRIVER` / `EV_EFI_RUNTIME_SERVICES_DRIVER`: Authenticode digest, `UEFI_IMAGE_LOAD_EVENT` with the file's buffer as location | every `LoadImage` |
| 7 | `EV_EFI_VARIABLE_AUTHORITY`: the db entry that allowed an image | once per entry |
| 5 | `EV_EFI_ACTION` "Exit Boot Services Invocation" and "... Returned with Success" | `ExitBootServices`, once |
| 8, 9 | `EV_IPL`: Xen's Multiboot2 ELF, dom0 kernel and initramfs (9), their command lines (8), as GRUB measures | the firmware's own Multiboot2 loader |

Nothing on the `ExitBootServices` path allocates (commands and digests on the stack, the log preallocated): the OS owns the memory map by then. The Linux stub measures its load options and initramfs into PCR 9 itself.

Cost: the firmware hashes what it measures in guest code. Debian's 12 MB kernel and 39 MB initramfs add about 2 s to a boot on an M5 Max (portable SHA-256 2.6 s; the SHA extensions 2.0 s, because the JIT does not compile them and the interpreter runs those blocks). Compiling `sha256rnds2`/`sha256msg1`/`sha256msg2` in the JIT is the next lever.

## Secure Boot (`secure_boot.rs`, `variable_store.rs`, `variables.rs`, `images.rs`)

- Keys (`crates/uemulator-firmware/secure-boot/`, provenance in its README): PK is a uemulator certificate whose private key was discarded when it was made, so nothing can sign a PK or KEK update; KEK is Microsoft's KEK CA 2011 and KEK 2K CA 2023; db is Microsoft Windows Production PCA 2011, Microsoft Corporation UEFI CA 2011, Windows UEFI CA 2023, Microsoft UEFI CA 2023 and Microsoft Option ROM UEFI CA 2023; dbx is the signature lists of Microsoft's current x64 dbx update (`dbx_x64.efiauth2`, signed with the 2023 KEK). Owner GUID of Microsoft's entries is `77fa9abd-...`, of the PK `f4157d1f-df64-482e-a25d-10b2385fb735`.
- Enrollment: with the handoff's Secure Boot flag (version 4, offset 0x378) and no PK in the store, the firmware enrolls KEK, db, dbx, then PK, persistently, with zero timestamps. Without the flag nothing is enrolled and nothing is removed: a machine that once had Secure Boot keeps its keys, shows `SetupMode` 0 and `SecureBoot` 0, and boots anything. There is no way yet to go back to setup mode short of wiping the nvram file.
- Variables: `SecureBoot` (decided at start-up: flag on and a PK), `SetupMode` (no PK; refreshed after PK changes), `VendorKeys` (1 until anything changes PK, KEK, db or dbx through `SetVariable`), `AuditMode` and `DeployedMode` 0, `PKDefault`, `KEKDefault`, `dbDefault`, `dbxDefault`, `SignatureSupport`, all read-only.
- Writes to PK, KEK, db, dbx, dbt and dbr (UEFI 2.9 8.2.2, EDK2's `AuthVariableLib`): attributes NV|BS|RT|TIME_BASED_AUTHENTICATED (plus `APPEND_WRITE`), `EFI_VARIABLE_AUTHENTICATION_2` in front, a timestamp later than the stored one unless appending, and in user mode a PKCS#7 signature over name || GUID || attributes || timestamp || data by the PK (PK, KEK) or a KEK or the PK (the databases). The attributes in the message include `APPEND_WRITE`: Microsoft's dbx updates verify only that way. In setup mode only a new PK is checked, against its own certificate. Appends skip signatures already present. Timestamps live beside the variable under `vartime/` in the same store. Other time-based authenticated variables are still refused.
- Image checks (UEFI 2.9 32.5, EDK2's `DxeImageVerificationLib`): an image whose hash (SHA-256/384/512) dbx lists, or one of whose signatures chains to a dbx certificate, or whose signing chain has a certificate dbx revokes by TBS hash, is refused; otherwise a signature chaining to a db certificate, or the image's hash in db, allows it; a signature whose digest does not match the image counts as none. `LoadImage` measures first, then checks (EDK2's order); a refused image gets a handle and `EFI_SECURITY_VIOLATION`, and `StartImage` refuses it (UEFI 2.9 7.4). The firmware's own uses of `LoadImage` (the supplied kernel, `xen.efi`) unload it and say why on the console. Its Multiboot2 loader refuses Xen under Secure Boot: an ELF has nothing to verify.
- The direct boot and the BIOS check nothing, so `secure_boot` without `uefi_firmware` is a `BadConfig`, and the CLI says to use `--firmware uefi`.

## Front ends

- CLI: `--tpm[=BOOL]` and `--secure-boot[=BOOL]` on every command with hardware options; `machine.toml` keeps `tpm` and `secure_boot`. A named machine's Secure Boot keys and TPM state live in its `nvram.kv`; `advanced boot` and the web page, which keep no store, give the TPM one in memory that lasts as long as the machine.
- Web: "TPM 2.0" (needs ACPI) and "Secure Boot" (needs UEFI) in Advanced, `?tpm` and `?secure-boot`, `OPTION_TPM`/`OPTION_SECURE_BOOT` (bits 11 and 12) in the C ABI. The page keeps no variables, so the keys are enrolled again on every load and the TPM is new on every load. `node hack/wasm/boot.mjs --tpm --secure-boot` passes them too.

## Verification

- Unit tests: the TPM engine and CRB interface (`dev/tpm/tests.rs`), ACPI (`a_tpm_adds_the_tpm2_table_and_its_device`), the handoff both sides, the machine (`machine::tests::tpm`), the crypto crate against FIPS vectors, openssl output and Microsoft's real certificates and dbx updates, the firmware's policy (`secure_boot.rs`) and authenticated writes (`variable_store.rs`: Microsoft's KEK-2011 and KEK-2023 dbx updates append in user mode; tampered, replayed, misdirected and wrongly-attributed ones are refused).
- Unit tests for keys, sessions and NV (`dev/tpm/key_tests.rs`) drive the TPM through a small TSS of their own that computes command HMACs, checks response HMACs and does the parameter encryption, so both sides of each formula are exercised: primaries, sealing, salted ECC and RSA sessions, PCR and PIN policies, contexts, persistence across a new device on the same store, NV, HierarchyChangeAuth (the response HMAC under the new value), Clear, ECDH. `dev/kv.rs` checks the guest cannot reach `tpm/` keys.
- Real guests (not tests): Debian 13's 6.12 kernel and initramfs with `--tpm` through the firmware: `tpm_crb` binds, `/sys/class/tpm/tpm0/pcr-sha256/*` and `binary_bios_measurements` exist, and replaying the log (the final events table's `ExitBootServices` events included) gives exactly PCRs 0, 1, 4, 5, 7 and 9. Under direct boot Linux finds the TPM unstarted and starts it itself. The same kernel with `--secure-boot` is refused ("nothing in db allows it"). An installed Debian 13 disk with `--secure-boot --tpm`: the firmware allows Debian's Microsoft-signed shim, shim verifies Debian's GRUB, GRUB boots Debian's kernel, Linux reports "Secure boot enabled" and lockdown and reaches its login prompt. GRUB's Xen entry is refused by GRUB itself (Debian's GRUB forbids `multiboot2` under Secure Boot). The web build under Node: `--tpm` and `--secure-boot` behave the same.
- Keys in a real guest (not tests): Debian 13's nocloud image (systemd 257, tpm2-tss 4) with `--tpm` on a `quick` machine: `systemd-analyze has-tpm2` says yes; `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7` enrolls a LUKS2 volume (ECC SRK made and persisted at 0x81000001) and `systemd-cryptsetup attach ... tpm2-device=auto` unlocks it, again after a restart of the emulator (the SRK comes back from `nvram.kv`), and not after PCR 7 is extended; `--tpm2-with-pin=yes` unlocks with the right PIN only. tpm2-tools: NV define/write/read/readpublic, RSA primary with seal/unseal, salted HMAC session from a saved context, ECC EK, changeauth, clear. Linux 7.3.1 built with `TCG_TPM2_HMAC` (and trusted keys) on the same disk: no TPM errors at boot, `/sys/class/tpm/tpm0/null_name` exists, cryptenroll and unlock work, and a trusted key is sealed under a persistent parent and loaded back through the kernel's own salted, encrypted HMAC sessions.
