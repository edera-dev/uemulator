# Milestones

**Status:** the project's status log, updated as work lands.

## Status

- M0-M3 done: kernel banner, VFS panic then `ExitReason::Reset`, and the Debian installer userspace (dialogs drawn) with both interpreter and JIT.
- M4 done: aarch64 JIT (block translator, inline TLB fast paths, ALU/mov/lea/push/pop/jcc/call/ret inlined, helper fallback for everything else, lazy-flag-aware jcc, per-page invalidation, self-modifying-code exit). ~5x faster than the interpreter (no-initrd boot: 6.4 s vs 32 s; roughly 300 MIPS). A lockstep verifier (`MachineConfig::verify_jit`, `--verify` in the example) runs the JIT against the interpreter per block; the whole installer boot is divergence-free.
- M6 done (see 11-storage-net-console.md): configurable RAM (`--mem`), virtio-pci disk, network and console (with resize), guest-verified: ping through the gateway responder, `stty size` follows `resize()`, disk read/write through `virtio_blk`.
- M5 partly done: realtime idle (`ClockMode::Realtime`), raw tty in the example, fixed RTC time option, aarch64 block chaining and wide inline lowering (see 06: roughly 3-4x over the M4 JIT; no-initrd Alpine boot 4.8 s -> 1.3 s CPU, initrd boot to the installer 13.9 s -> 4.7 s, interpreter ~60 s, lockstep-verified over the whole no-initrd boot). Not done: guest register caching, dead-flag elimination, LAPIC/IOAPIC, SMP.

- Machine lifecycle done: a guest reset reboots the machine in place by default (`MachineConfig::reboot`, CLI `--no-reboot` to end with `ExitReason::Reset`; checked on the real Alpine kernel with `busybox reboot -f`, interpreter and JIT), `hlt` with IF=0 is `ExitReason::Shutdown` (checked with `busybox poweroff -f`; the UEFI hardware-virtualization loop applies the same rule, but has no in-process reboot). `ConsoleKind::Virtio` (hvc0) is the default everywhere except the UEFI hardware-virtualization path (no virtio in `Platform`). The M2 criterion "VFS panic then clean Reset" now needs `--no-reboot`; by default `panic=-1` reboots forever.

- Workspace split done: `crates/uemulator` (library) + `crates/uemulator-cli` (`uemulator quick create|edit|boot|reinstall|update-artifacts|list|show|delete` for named machines and `uemulator advanced boot|boot-firmware`, clap). 
- `jit` feature (default on) gates `libc`/`windows-sys`; `--no-default-features` is dependency-free and interpreter-only.
- x86_64 host JIT done (see 06): same inlined subset as aarch64, verified in lockstep. Exercised on macOS x86_64 under Rosetta; Linux and Windows x86_64 hosts compile but are untested.

- Instruction extensions done (see 03, "Instruction extensions"): POPCNT/LZCNT, CMPXCHG16B, SSE3, SSSE3 (XMM forms), SSE4.1, SSE4.2 (incl. CRC32 and pcmp[ei]str[im]), PCLMULQDQ, AES-NI, MOVBE and FSGSBASE are implemented and advertised in CPUID (leaf 1 ECX, 0x80000001 ECX, leaf 7). The Alpine boot now executes cmpxchg16b, popcnt, pshufb and palignr in the kernel. Not advertised: VMX.

- SVM done for 64-bit guests (see 03): vmrun/vmload/vmsave/stgi/clgi/invlpga, intercepts, event injection, nested paging, TSC offset; tested with hand-built VMCBs (interpreter and JIT); since validated against KVM and Xen (see 18, step 6).

- Guest I/O round 1 done (see 23): network round trips no longer wait out sleep timers (29x TCP request/response), the syscall path's `swapgs`/`clac`/`stac`/`cli` continue JIT blocks and are inlined with `push imm` (1.3x syscalls), `rep stos` of wide elements is one host fill (2.6x memset), realtime device ticks are rate-limited.

- ERMS/FSRM done: byte-sized rep slices make `rep movsb` copy-heavy guest workloads ~12x faster (03).

- Live CDs and several drives on the web done (see 13, 19): the page attaches up to eight drives, ISOs read-only, and offers up to 2047 MiB (the most one allocation can be on wasm32; JavaScript reads the module's pointers as unsigned past 2 GiB). At 1 GiB Fedora 44's Server netinst fails exactly as a user saw (`Initramfs unpacking failed: write error`, then `VFS: Unable to mount root fs` on the `drm_panic` screen); at 2047 MiB it reaches Anaconda on the CLI, and on the wasm module under Node it unpacks its initramfs and starts stage 2 from the read-only ISO. Fedora 44 KDE Live's `root=live:CDLABEL=` mounts `/sysroot` from the ISO on `vda` (CLI, direct kernel). The firmware boots a plain El Torito ISO's EFI image: netboot.xyz's iPXE on the CLI and in the page. Not done: BIOS El Torito (isolinux-only ISOs such as Tiny Core's) and a real CD device (`sr0`).

- AVX, AVX2, FMA and F16C done (see 03): VEX.128/256 through the SSE kernels, YMM upper state in XSAVE, gathers, masked moves, a fused multiply-add on the soft-float engine, half-precision conversion. Found while booting Debian: a register-collision bug in the VEX staging that broke glibc's AVX2 `strcmp`, now covered by tests.

- BIOS boot of a disk done (see 17): `MachineConfig::boot_disk` runs the first sector in real mode with the BIOS services as host code, enough for Alpine's syslinux 6.04 to load the installed kernel and boot it to a login prompt; `quick boot` uses it once the disk is not blank.

- Real mode, 16/32-bit protected mode, compatibility mode and virtual-8086 mode done (see 15): mode derived from CS, a mode-aware decoder, segment bases and limits, 16/32-bit interrupt and call-gate delivery, hardware task switching, sysenter/sysexit, and `MachineConfig::firmware` / `uemulator advanced boot-firmware` to boot a real-mode image. 49 tests in `cpu/legacy_tests.rs`. The JIT stays 64-bit-only.

- Non-long-mode paging done (see 04 and 03, "Control-register rules outside long mode"): paging off, 32-bit two-level paging (4 MiB pages, PSE-36 advertised), PAE with latched PDPTEs, and the CR0/CR3/CR4/EFER transition rules; 82 tests in `cpu/paging_tests.rs`.

- AVX-512 done (see 03, "AVX-512"): EVEX decoding, 32 ZMM registers, opmasks and XSAVE components 5-7, AVX512F/VL/BW/DQ/CD/IFMA/VBMI/VBMI2/VNNI/BITALG/VPOPCNTDQ, GFNI, VAES and VPCLMULQDQ, with masking, broadcast, embedded rounding and fault suppression; advertised in CPUID. Alpine and the Debian installer boot with it on. **Correction:** this entry (and the AVX one above) claimed more than was true. Unit tests covered the instructions that existed, but `vpsubsw` (EVEX) and `vdbpsadbw` were #UD while AVX512BW was advertised, which only a real guest running one of every intrinsic showed; both are fixed, as are AVX512_BF16 and SHA-NI (added), and 03 ("Real-guest check") records how AVX was verified in a guest against QEMU TCG, under signals and context switches, and JIT versus interpreter.

- SVM validated against Linux KVM (see 03, "SVM", and `hack/kvm/run.sh`): the emulated Alpine guest loads `kvm_amd` and runs vCPUs in real, protected, long, PAE and 32-bit-paging mode on the emulator's SVM and nested paging. A 32-bit Alpine i686 kernel also boots to a shell (see 15).

- Zen 4 CPU model done (see 03, "CPUID/MSR contract"; `cpu/cpuid.rs`): family 19h model 11h (EPYC 9004 Genoa), cache, TLB and topology leaves (0xB, 0x8000001D/1E) consistent with a configurable processor count and x2APIC id, SHA-NI, ADX, CLWB/CLFLUSHOPT, RDPID, CLZERO, WBNOINVD, AVX512_BF16, XSAVEC/XSAVES/XGETBV1 with the compacted format, 1 GiB pages, and the AMD configuration MSRs Linux and Xen touch. Linux reports "AMD EPYC-Genoa Processor", `sha_ni avx512_bf16 xsavec xsaves clzero rdpid ...` and the compacted XSAVE format.

- Zen 5 CPU model done, replacing Zen 4 (see 03, "CPUID/MSR contract" and "Speculation control", and 21, "Zen 5 Turin model"): family 1Ah model 02h stepping 1 (EPYC 9005 Turin), Zen 5 caches and leaf 0x80000026, Turin's speculation controls in the AMD spelling only (automatic IBRS, SBPB, PSFD, BTC_NO...), AVX-VNNI, MOVDIRI, MOVDIR64B, AVX512_VP2INTERSECT and PREFETCHI. Linux 6.18 reports no vulnerability as "Vulnerable" without `mitigations=off`, which the default command line no longer passes; boot time is unchanged.

- UMIP, SMEP/SMAP, PCID/INVPCID, MONITOR/MWAIT, RDTSCP done (see 03).

- VEX decoding, BMI1 and BMI2 done (see 03, "VEX and BMI").

- Speculation control, XSAVE and RDRAND done (see 03, "Speculation control" and "XSAVE and RDRAND"): guests see an in-order CPU immune to every speculative-execution bug (no retpolines, return thunks, KPTI or VERW), use `xsaveopt` for context switches, and seed the crng from `rdrand`/`rdseed`.

- AMD IOMMU done (see 16): `MachineConfig::iommu(true)` adds PCI function 00:00.2 with the IOMMU and MSI capabilities, the MMIO registers, command buffer, event log, device table, 1-6 level I/O page tables (large and arbitrary-size pages), an IOTLB, DMA translation for every virtio function through `GuestMem::with_dma`, interrupt remapping (32- and 128-bit IRTEs) behind `Iommu::remap_interrupt`, and an IVRS table builder. XTSup (x2APIC IRTEs, IntCapXT) came with the ACPI work; a Debian 6.12 guest enables interrupt remapping and x2APIC on it and runs virtio-net through it (16).

- WebAssembly port done (see 13): `crates/uemulator-web` + `hack/web.sh serve`; a Web Worker with an xterm.js console, boots Alpine to a busybox shell in Chrome. A WebAssembly JIT (blocks become modules the page instantiates; `jit/wasm.rs`) runs hot code about 9x faster than the interpreter there; the differential tests run on `wasm32-wasip1` under Node. No disk or network. Later: streamed disks, and a network the tabs share (13, "The shared network": `SegmentAgent`, BroadcastChannel, a Web Lock electing the DHCP server; `hack/wasm/segment.mjs` checks addresses, ping, TCP and a server handover).

- UEFI application done (see 12): `crates/uemulator-uefi`, library `no_std` on `target_os = "uefi"`, `hack/uefi/boot.sh`; emulator (interpreter) everywhere, plus a hardware-virtualization path on x86_64 (AMD SVM verified under TCG, Intel VMX untested), no disk/net.

- Interrupt controllers and CPU platform state for Windows done (see 07, "LAPIC and IOAPIC"): xAPIC and x2APIC local APIC with timer and TSC-deadline, 24-pin I/O APIC fed by the same device lines as the PIC, CR8/TPR priority, NMI delivery with `iret` unblocking, MTRRs, PAT validation, inert machine-check banks, AMD memory-typing MSRs, CPUID leaf 0xB. The Alpine kernel boots with the APIC advertised (virtual wire mode, TSC-deadline timer). SMP is done (below). The HPET, the ACPI PM timer and ACPI tables are done (below).

- Guest 3D, device side (M1 of 25) done: `MachineConfig::gpu(GpuLink)` makes the virtio-gpu offer `VIRGL` and the embedder's capsets, and forwards contexts, 3D resources, transfers in both directions and `SUBMIT_3D` streams to the renderer as `GpuCommand`s, holding every fenced response until the renderer passes its fence. Covered by the `Rig` tests in `dev/vgpu/tests/three_d.rs` with the test as the renderer; no renderer exists yet, so no guest has drawn through it. A machine without a renderer is unchanged.
- Guest 3D, web spike (M0 of 25) done: `?gpu` on the page gives the guest a virgl GPU drawn by a render worker. Its WebGL2 canvas sits over the screen, and the capsets come from `crates/uemulator-virgl`. In an Alpine guest with Mesa from edge (3.24's Mesa has no virgl), `hack/gpu/eglclear.c` reports `GL_RENDERER: virgl` and its clears reach the canvas. Fences complete and the guest does not hang. Only clears are drawn. `node hack/wasm/boot.mjs --gpu` runs the same without a browser.

## UEFI firmware (docs/plans/19)

Done: `MachineConfig::uefi_firmware` and `key_value_store`, `crates/uemulator-firmware`, `advanced boot-uefi`, `quick` machines with `firmware = "uefi"`. Exit criteria met in a real guest: the Linux EFI stub and Debian GRUB 2.12 boot Alpine from a GPT ESP, and a variable written by Linux survives a guest reset through the nvram file. Open: Xen (`xen.efi`, multiboot2), Fedora shim, ACPI tables in the handoff.

- UEFI is the default firmware and boots kernels (see 19): `--firmware uefi|bios|none` on `quick create`/`edit` and `advanced boot`, `uefi` by default, a `machine.toml` without the key loads as `uefi` (existing machines installed under the old BIOS default need `firmware = "bios"`). `MachineConfig::uefi_firmware` now combines with `kernel`/`initrd`/`cmdline`: the library places them at the top of RAM, the firmware boots the kernel first (EFI stub required, else `new` fails with a `firmware none` hint) with the initramfs behind a `LoadFile2` on `LINUX_EFI_INITRD_MEDIA_GUID`. `none` is the old direct 64-bit boot. Installer boots of a `uefi` machine keep its `nvram.kv`. Checked: a hand-built EFI kernel on the real firmware (command line and initramfs size, CLI test), and the Alpine 6.18 netboot kernel and initramfs through UEFI (`efi: EFI v2.9 by uemulator`, `INITRD=`, ACPI, DHCP over the NAT, same behaviour as `none`; `--verify` has no divergence). Not checked here: a complete install and disk boot under UEFI (the installer's `apk` could not fetch its index in this environment, with or without UEFI), Debian's installer.

- SMP done (see 03, "SMP"; step 4 of `docs/plans/18-xen-dom0.md`): `MachineConfig::cpus(n)`, `--cpus N` on the CLI and `cpus` in a `quick` machine's `machine.toml`, 1 to 64, default 1. One `Cpu` per vCPU over one host thread, cooperative round robin with a 4096-instruction quantum, a switch at `hlt`/`mwait`/`pause`, the machine-wide state (RAM, devices, JIT) moved between vCPUs rather than duplicated, a clock that divides instruction counts by the number of running vCPUs, per-vCPU local APICs with IPIs of every addressing mode, INIT/SIPI start-up into real mode, MSI/I/O APIC/IOMMU destinations routed to the right APIC, per-vCPU CPUID ids and topology. Checked in real guests: Alpine 6.18 with 4 and 64 vCPUs on the JIT and 4 on the interpreter (`nproc`, distinct apicids, `Total of N processors activated`, no RCU stalls or watchdog reports, a pthread mmap/mprotect/munmap + spin lock + fork stress and four parallel `md5sum`s correct, CPU offline/online through sysfs), and the Debian trixie 6.12 kernel with `--iommu` (x2APIC cluster mode with interrupt remapping). A parallel workload takes about a third of the guest time of the serial one on 4 vCPUs. Not done: `--verify` with more than one vCPU (refused), firmware and BIOS-disk boots with more than one vCPU (refused). Real parallelism is done (below).

- Xen 4.21 boots on the emulated Zen 4 machine (see 18, step 6): GRUB multiboot2 or `xen.efi` from the UEFI firmware, a PVH Alpine dom0 to its login prompt in 26 s of host time, `xl info`, `xl list` and a PVH domU running its initramfs. Seven emulator bugs fixed on the way (compatibility-mode returns, EFER.LMA at #VMEXIT, IOMMU/FCH overlap, stale JIT blocks after SVM exits, MMIO clock skew in the JIT, MADT/`_PRT` polarity, 16550 input pacing). Fedora 44 cloud image boots to a root login through shim and GRUB on 4 vCPUs and installs Xen 4.21.2 with dnf over the NAT; its Xen entry is not yet booted. Open: `xen.efi` through GRUB's chainloader, Fedora Xen dom0.

- Xen as the machine's hypervisor (see 18, "Xen as the machine's hypervisor"): `MachineConfig::hypervisor` takes `xen.gz`, `xen` or `xen.efi` and the UEFI firmware boots it with the machine's kernel as dom0, `xen.gz` through a Multiboot2 loader of its own (GRUB's UEFI behaviour: relocated, EFI amd64 entry, boot services kept) and `xen.efi` through Edera's `XEN_EFI_*_MEDIA` media loaders; handoff version 3; a gzip decoder in the library (no dependency). CLI `advanced boot --hypervisor`, the web page's Hypervisor field and its "Edera Xen" demo (Xen pinned by digest in `hack/web/demo-xen.ref`). Checked: Edera's Xen 4.22 builds a PV Alpine dom0 to a shell both ways on the CLI, with 1 and 2 vCPUs, and through `xen.gz` in a browser (the desktop app's pane) and under Node (24 s). `quick create`/`edit --hypervisor` keep a copy of the image in the machine's directory and run installer boots under it (Alpine's netboot as a PV dom0 with its NAT NIC, modloop download and disk; 2 vCPUs, `dom0_mem`, power-off; `xen.efi` given for one boot); an installed disk is refused with a hypervisor. Not done: a hypervisor without UEFI (`--firmware none`).

- JIT performance (see 20): direct block chaining for same-page static exits, inline shl/shr/sar at 8/16 bits, shlx/shrx/sarx/bzhi/andn/blsr group, adc/sbb, dead lazy-flag records skipped, hardware carry-less multiply for pclmulqdq, unmasked EVEX commits by lane, `--debug` histogram of what still reaches the interpreter. The 252 MB Fedora netboot initramfs unpacks in 14.7 s of host time instead of 22.1 s on an Apple Silicon host (`hack/perf/unpack.sh`).

- Xen boot speed (see 20, round 3, and 18): RTC update-in-progress, SVM TLBs swapped instead of flushed at VMRUN/#VMEXIT (ASID, TLB_CONTROL, INVLPGA), a nested-leaf cache, live-flag rotates on the WebAssembly backend, a direct-mapped IOTLB and cached device table entries, a #VMEXIT histogram in `--debug`; fixed: nested write-protection and NX were bypassed after a read cached a page. The demo's PVH dom0 shell in 3.5 s natively and 14.1 s under Node (was 4.3 s and 16.7 s), PV 20.5 s under Node (was 23.7 s); `hack/perf/xen.sh` measures it. Next: hand Xen the dom0 ELF instead of the bzImage (1 s natively, 2 s under Node of Xen's gunzip).

- SMP on host threads done (see `docs/plans/22-smp-threads.md`): `SmpMode::{Auto, Timeshare, Threads}`, `MachineConfig::smp`, `MachineConfig::thread_spawner`, `--smp` on the CLI. With the realtime clock (the default) and more than one vCPU every vCPU runs on its own host thread, with its own decode cache and a handle on the one shared, position-independent JIT cache (blocks keyed by physical address; 193k blocks and 58 MiB for an Alpine boot, was 1.64M and a flush), over shared RAM (`ram::GuestRam`), shared code-page flags and devices behind a reentrant device lock (`dev::handle`); a device thread ticks them; an exclusive section stops the world to flag a page as code (revoking every vCPU's write tags) and to run locked accesses no host atomic covers; stale translations are invalidated through a log and per-vCPU attention words; guest accesses are acquire/release (`ldar`/`stlr` in the aarch64 JIT), locked instructions and `xchg` are compare-exchanges with retry, page-table A/D updates are compare-exchanges. Freestanding hosts keep time-sharing unless the embedder gives a spawner and a host clock. Alpine 6.18 runs with 4 and with 64 vCPUs on threads (tsc clocksource, hot-plug, fork storm, four parallel hashes in the time of one); fixed on the way: MONITOR now arms its line (a store between MONITOR and MWAIT was lost, which only threads can provoke).

- Guest RAM up to 1 TiB less the PCI hole (see 04, "Physical"): RAM past 3 GiB is mapped from 4 GiB up, the 3 GiB..4 GiB hole belongs to the devices, and `MAX_MEMORY_MIB` is bounded by the 40-bit physical address width instead of the old 3072 (no check against host RAM; memory is committed as the guest touches it). e820, the UEFI handoff map, `TOP_MEM2`, the boot page tables (1 GiB pages above 4 GiB) and every "is this RAM" check in the CPU, the page walker, the JIT and DMA follow the layout. Checked: the Fedora 44 netboot kernel and initramfs with 8192 MiB through the built-in UEFI firmware (e820 `0x100000000-0x23fffffff` usable, `Memory: 7567612K/8386232K available`, dracut starts) and with 6144 MiB under `--firmware none`. Not checked: guests above the host's RAM size (the guest has to touch the memory to commit it), the `bios` firmware with RAM above 4 GiB (int 15h E820 reports it; a real-mode loader cannot use it).

- Disk images (see 11, "Devices", and `docs/spec/uemulator-disk-format.md`): the udisk copy-on-write format in the library (`no_std`, so the web and UEFI builds have virtio-blk), `uemulator disk create|convert|info`, `--disk` that opens raw or udisk and follows an overlay's base locally or over HTTP, and new machines on `disk-<n>.udisk`. The web page streams one raw or udisk disk from a URL or a picked file with writes in memory. Checked: the Alpine disk of an installed `uefi` machine (32 GiB raw, 3.7 GiB used) converts to a 3.2 GiB udisk in 16 s, and boots through the UEFI firmware to its login prompt from an overlay over it, with the base both local and streamed from `hack/web/serve.py`; flattening an overlay back to raw is byte-identical.

- TPM 2.0 and Secure Boot (see 26): `MachineConfig::tpm` (a CRB TPM with the measured-boot command set, ACPI TPM2 and `MSFT0101`) and `MachineConfig::secure_boot` (the firmware enrolls a uemulator PK and Microsoft's KEKs, db and dbx and checks every `LoadImage` against db and dbx, with authenticated writes to PK, KEK and the databases), `--tpm`/`--secure-boot` on the CLI and the web page, `EFI_TCG2_PROTOCOL` with a crypto-agile event log and final events table, handoff version 4, and `crates/uemulator-crypto`. Checked: Debian 13's kernel through the firmware with `--tpm` (`tpm_crb` binds; the log replays to PCRs 0, 1, 4, 5, 7, 9), an installed Debian 13 disk with both on (shim, GRUB, the kernel with "Secure boot enabled" and lockdown, login prompt), the same kernel booted directly refused under Secure Boot, and the web build under Node. Measuring costs about 2 s per boot for Debian's 51 MB of kernel and initramfs. Not done: TPM keys, sessions and NV; a way back to setup mode.
